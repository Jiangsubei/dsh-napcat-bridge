## 1. 调研 1.1：`agentsService.create()` 带 fork 参数的调用方式

### 1.1 API 签名与接口定义
在 `@deepseek-ai/dsh-agent`（`lib/types/index.d.ts`）与 `@deepseek-ai/dsh-agent-loop`（`lib/index.js`）中，`agentsService.create` 签名如下：

```ts
export interface CreateAgentOptions {
    /** 唯一的会话与代理 ID */
    readonly sessionId: SessionId;
    /** 会话元数据 */
    readonly meta?: {
        readonly cwd?: string;
        readonly parentSession?: SessionId;
        readonly isSeeded?: boolean;
        readonly origin?: 'subagent';
        readonly delegationDepth?: number;
        readonly agentPreset?: string;
        readonly allowedTools?: readonly string[];
    };
    /** 继承事件的前缀长度（与 seed.length 一致） */
    readonly inheritedEventCount?: SessionLogOffset;
    /** 继承的历史事件切片（从 seq 0 到最后一个已完成 turn 边界） */
    readonly seed?: readonly SessionEvent[];
    /** 模型与提供商参数 */
    readonly agentOptions?: AgentOptions;
    readonly signal?: AbortSignal;
    readonly setup?: AgentSetup;
}
```

### 1.2 关键事实与行为确认
1. **不支持 `{ fork: sessionId }` 简写参数**：`agentsService.create()` 不接受单字段 `fork`，而是接收标准的 `seed` + `inheritedEventCount` + `meta` 配置。
2. **DSH 官方标准 fork 机制（参照 `dsh-api-session-controller/lib/index.js:655-720`）**：
   - 从父会话（`parentSession`）的 `parentSession.snapshotEvents()` 中取得所有事件。
   - 寻找最后一个 `turn/end` 事件 `boundary`，切片位置 `cut = boundary.seq + 1`，跳过后续未进入 `turn/start` 的间隙事件。
   - 传入：
     ```ts
     {
       sessionId: reviewSessionId,
       seed: parentEvents.slice(0, cut),
       inheritedEventCount: cut,
       meta: {
         cwd: parentSession.header?.cwd,
         parentSession: parentSession.header?.id || parentSession.id,
         isSeeded: true,
         origin: 'subagent',
         allowedTools: ALLOWED_MEMORY_REVIEW_TOOLS,
       },
       agentOptions: {
         provider: reviewModel?.provider,
         model: reviewModel?.model,
       }
     }
     ```
3. **驱动与等待方式**：
   - `create()` 返回 `AgentHandle`（`{ id, agent, dispose() }`）。
   - 向 review agent 发送 prompt 时，构造 `UserMessage` 并调用 `handle.agent.followup(userMsg)`。
   - 等待 review agent 执行完成必须调用 `await handle.agent.whenIdle()`。
4. **Workspace Registry 自动注册情况**：
   - `WorkspaceRegistry` 没有监听 `session/created` 事件。通过 `agents.create()` 创建的 session **不会**自动挂载到任何具体工作区的 `sessionIds` 中（属于独立/未分组会话）。
   - 但是底层 `dsh-session` 会通过 `sessionPersistence.create()` 在磁盘目录写入文件，因此全局扫描（`sessionPersistence.list()`）是可见的。这也是为什么需要进行物理清理（见 1.2）。

## 2. 调研 1.2：Session 物理删除的可行路径

### 2.1 物理存储结构验证
实机检查 `~/.dsh/sessions/` 验证确认：
- 根目录：`~/.dsh/sessions/`
- 工作区目录：`--home-nyara-.dsh-workspace-napcat--/`（由 `projectKey(cwd)` 编码）
- 会话目录：`<sessionId>/`
- 文件：`<sessionId>/session.jsonl.zstd`

每个 Session 独占一个子目录：`~/.dsh/sessions/<projectKey>/<sessionId>/`。

### 2.2 物理删除操作链（对齐 `dsh-archive-manager`）
参照 `~/dsh-archive-manager/src/workspace.js` 中的 `deleteSessionCore`，完整且安全的操作链路如下：

1. **持久化刷新与实时会话分离**：
   ```ts
   const sessions = ctx.get('sessions') || (ctx as any).sessions;
   const live = sessions?.get(sessionId);
   if (live) {
     await sessions.flush(live);
     const entry = sessions.liveEntryFor(live);
     sessions.detachEntered(entry);
   }
   ```
2. **清理投影缓存（如果存在）**：
   ```ts
   const projCache = ctx.get('sessionProjectionCache') || (ctx as any).sessionProjectionCache;
   await projCache?.whenIdle?.();
   await projCache?.delete?.(sessionId);
   ```
3. **清理 Spill 临时文件**：
   `@deepseek-ai/dsh-spill-local` 导出了 `sessionDir(root, sessionId)`：
   ```ts
   import { sessionDir } from '@deepseek-ai/dsh-spill-local';
   const spill = ctx.get('spillStore') || (ctx as any).spillStore;
   if (spill?.root) {
     await rm(sessionDir(spill.root, sessionId), { recursive: true, force: true }).catch(() => {});
   }
   ```
4. **定位并彻底删除物理转录工件目录**：
   `ctx.get('sessionPersistence')` 提供了 `locate(header)`：
   ```ts
   const persistence = ctx.get('sessionPersistence') || (ctx as any).sessionPersistence;
   let targetDir: string | undefined;
   if (persistence?.locate) {
     const loc = persistence.locate(header || { id: sessionId });
     if (loc?.path) {
       targetDir = path.dirname(loc.path);
     }
   }
   // Fallback: 若 locate 不可用，扫描或推导 ~/.dsh/sessions/*/<sessionId>
   if (!targetDir) {
     targetDir = findSessionDirectoryFallback(sessionId);
   }
   if (targetDir) {
     await rm(targetDir, { recursive: true, force: true });
   }
   ```
5. **释放 Agent 句柄**：
   ```ts
   await handle.dispose();
   ```
6. **清理内存索引**：
   从 `workspaceRegistry` 中遗忘该会话（见 1.4）。

## 3. 调研 1.3：Tool Call 计数的提取方式

### 3.1 事件定义查证
在 `@deepseek-ai/dsh-session`（`lib/types/types.d.ts`）中：
- `'turn/start'`: `data: { turn: number }`
- `'turn/end'`: `data: { turn: number, reason: TurnEndReason }`
- `'tool/call'`: `data: { turn: number, step: number, callId: ToolCallId, name: string, arguments: string }`

### 3.2 提取逻辑实现
在 `session/event` 的 `turn/end` 阶段：
1. `session.snapshotEvents()` 返回当前 session 内存中截至当前的所有事件。
2. 提取当前 turn 的工具调用数：
   - 优先通过 `e.type === 'tool/call' && e.data?.turn === currentTurn` 精确统计；
   - 若 `currentTurn` 不存在，寻找最后一个 `turn/start` 的 seq（`startSeq`），统计 `seq >= startSeq && seq <= event.seq && e.type === 'tool/call'`；
   - 若依然为 0，保留原有 `event.data?.toolCallsCount` 或 `event.data?.tool_calls?.length` 作为 fallback。
3. 这样保证了 100% 捕获模型发起的工具调用，彻底修复 Bug 3 中 tool calls 门控无法触发的问题。

## 4. 调研 1.4：Workspace Registry 的 Header 移除方式

### 4.1 接口与内部状态
- `WorkspaceRegistry` 类**没有**对外公开针对单个 session 的 `deleteSession`、`removeSession` 或 `forget` 方法（其唯一的 `delete` 方法是 `delete(id: WorkspaceId)`，用于删除工作区）。
- 但在 JS 运行时，其内部通过 `this.headers`（`Map<SessionId, SessionHeader>`）、`this.sessionPaths`、`this.invalidSessionPaths` 维护会话索引。
- 可以直接执行安全清理：
  ```ts
  const wsRegistry = ctx.get('workspaceRegistry') || (ctx as any).workspaceRegistry;
  if (wsRegistry?.headers && typeof wsRegistry.headers.delete === 'function') {
    wsRegistry.headers.delete(sessionId);
    wsRegistry.sessionPaths?.delete(sessionId);
    wsRegistry.invalidSessionPaths?.delete(sessionId);
  }
  ```

### 4.2 墓碑机制评估
- `dsh-archive-manager` 引入墓碑是因为在前端 UI 上用户可能多次触发删除，或者存在冷复用探针避免已被删除的会话被重新读入；
- 而在 Bridge 的后台回顾中，Review Session 是**物理完全删除**（磁盘文件被 `rm -rf` 销毁），任何后续的 `sessionPersistence.list()` 扫描磁盘绝不可能再扫描到该目录；
- 因此，无需常驻复杂的墓碑簿记类，直接在物理删除后清理 `wsRegistry.headers` 即可。

### 4.3 Session 编号回退修复（任务 4）
- 在 `SessionManager.peerToSessionId()` 中扫描 `wsRegistry.headers` 与 `db.getSessionState(peer)` 时，验证候选 session 的物理存在性（通过 `sessionPersistence.locate()` 或推导路径检查文件是否存在）。
- 若物理文件不存在：
  - 从 `wsRegistry.headers` 中清理；
  - 从 `known` Map 中清理；
  - 从 `this.peerCurrentSessionId` 内存 Map 中清理；
  - 清理 DB 中的 `current_session_id`。
- 这样，当物理删除旧 session 后，新建 session 的编号将自动回退到 1，彻底解决编号不断膨胀的问题。
