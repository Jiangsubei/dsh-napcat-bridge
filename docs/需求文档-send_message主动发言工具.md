> **文档版本**: v0.1（草稿，待审阅批注）
> **日期**: 2026-09-07
> **状态**: 设计讨论收敛，待用户审阅批注后定稿

## 0. 背景与问题

### 0.1 问题
- 模型的约束（行为准则："工具调用之间不要产生正式回复"）**不可靠**——模型不知道自己后面是否还有工具调用，把"边想边说"写成普通文本块。
- 实测日志（group 1093179234）：中间泄漏消息**全部是与 tool-call 同一条 assistant/message 的文本块**（旁白/思考溢出），真正该发的终答是无工具调用的独立 assistant 消息。
- 直接约束模型无效；但用户**有时**确实希望模型在长任务中间主动汇报进度。

### 0.2 结论：约束模型 → 应用层结构性强制 + 工具化发言
- 与 tool-call 同块的文本（旁白）**永不自动发送**（结构判据，应用层强制）。
- 模型想向 QQ 发言，**必须调用 `send_message` 工具**（工具化出口，显式、可引导）。
- 配一条 **QQ 会话动态段**（系统提示词最前）告诉模型发言协议。
- **turn/end 兜底**：整轮 0 次 send_message → 自动补发终答（防静默），路径与现状一致。

## 1. 需求 A：send_message 工具

### 1.1 签名与语义（v1 定稿）
```
send_message { text: string }
```
- **作用**：向**当前绑定的 QQ 会话**（群聊/私聊）主动发送一条文本。
- v1 **仅 text 单参数**；`reply_to`（引用某条消息）/`at`（艾特某人）**不做**，留作可选参数扩展位（见 §5）。

### 1.2 注册范围
- **仅普通 QQ 会话**（`qq-group-*` / `qq-user-*`）注册可见。
- 非 QQ 会话（外部 WebUI 等）**不注册**（沿用 tools.guard 注册模式）。
- Background Review / 加好友专用 Session 等受限沙箱**不注册**（无发言权）。
- 区别于 `react_message`（仅群聊）：send_message **群聊/私聊均可用**。

### 1.3 出站处理
- 走**现有串行队列 + stripMarkdown** 管线（与正常回复同待遇）；长文本自动分段。
- 成功返回 `message_id`。
- 不自动携带 @ / 引用前缀（那是自动回复路径的行为；模型主动发言是另一语义，见 §5）。

### 1.4 报错（真实分支收敛）
| 场景 | 行为 |
|---|---|
| 文本为空 / 纯空白 | `{ success: false, error: "发送内容不能为空。" }` |
| NapCat 发送失败 | `{ success: false, error: "消息发送失败: {retcode/wording}" }` |
| 成功 | `{ success: true, message_id, sent_preview }` |
| 无 QQ 会话上下文 | **防御性守卫**（正常不触发，注册层已挡），报"send_message 需在 QQ 会话中执行" |

> 注：**不存在"NapCat 未连接"分支**——QQ 消息能进来就说明连接活着，回合本身以连接为前提。

### 1.5 工具描述（模型引导）
```text
send_message: 向当前 QQ 会话（群聊/私聊）主动发送一条文本给用户。
- 长任务进行中：向用户汇报进度或说明需要等待
- 任务完成时：发送最终答复（务必用本工具发）
- 每条 text 为一条独立 QQ 消息，过长自动分段
```

## 2. 需求 B：QQ 会话动态段（系统提示词最前）

### 2.1 设计
- 新增 `systemPrompt.context` 动态段（名如 `napcat:qq_scenario`），**order 取最低**（现有：记忆 40 / 人格行为 50，本段 ~10），排在动态段**最前**。
- 仅对 QQ 会话（qq-group-*/qq-user-*）返回内容；非 QQ 会话返回空串（沿用现有 gate 模式，缓存友好、fork 继承）。
- **只讲协议，不讲策略**（何时该说什么归行为准则）；**不告知 turn/end 兜底**（隐形安全网，防模型偷懒）。

### 2.2 段文本（定稿）
```text
# 如何发送消息

你正在 QQ 聊天中与用户对话。

【如何把内容送达用户】
- 想向用户发送文字/答复，必须调用 send_message 工具——你写在回复正文里的文字不会发送到 QQ，仅作内部记录。
```

> 不再赘述 react_message / send_file / 场景细节——入站消息与工具描述已自明，节省 token。

## 3. 需求 C：出站旁白抑制与 turn/end 兜底（OutboundStreamBridge 改动）

### 3.1 旁白结构性抑制（根治泄漏）
- **与 tool-call 同一条 assistant/message 的文本块：永不自动发送**（结构判据，应用层强制），仅留 Web UI 记录。

### 3.2 turn/end 兜底（防静默）
- 每轮跟踪 `send_message` 工具调用次数：
  - **0 次** → turn/end 自动补发**终答文本**（回合内最后的正式文本），**路径与现状一致**（含 at/引用前缀逻辑）
  - **≥1 次** → 信任工具，不自动补发（模型自管理输出；其后的正文文本留 Web UI）
- 取舍（接受）：模型若先 send_message 报进度、末尾偷懒写文字终答——该文字**不补发**（Web UI 可见）。由工具描述引导规避。

### 3.3 实现前待核实（DSH 运行时）
- DSH agent-loop 是否保证"**无工具调用的 assistant 文本消息 = 回合结束**"（决定"终答文本"识别方式；实测日志符合，仍需源码确证）。
- turn/end 时"终答文本"的取法（最后一条 assistant/message 的 text 块）与 send_message 计数的事件类型（tool/call name === 'send_message'）。

## 4. 边界与取舍汇总

| # | 场景 | 处理 |
|---|---|---|
| 1 | 模型先 send 报进度、末尾纯文本写终答 | 终答不补发（Web UI 保留），接受 |
| 2 | 模型连续多次 send_message | 每条独立消息，串行队列保序 |
| 3 | send 后又写重复正文 | 正文不自动发，不重复轰炸 |
| 4 | 空文本 | 报错 |
| 5 | 超长文本 | 自动分段 |
| 6 | 私聊 | 正常可用 |
| 7 | 工具间隙旁白 | 结构抑制，永不自动发 |

---

## 5. 明确不做（v1 范围外）

- **`reply_to`（引用指定消息）**：v1 不做。理由：回合级自动引用已覆盖主流场景；模型引用更早消息需可靠 message_id（依赖 read_chat_history 暴露 id 且与出站 CQ:reply 同一 id 空间——后做时核实）。触发条件成熟（真实出现需求）再加，可选参数不破坏兼容。
- **`at`（艾特指定用户）**：v1 不做。@错人是公开事故且模型可靠提取 qq 不可控；若后做需"模型显式传 qq + 服务端校验该 qq 在群内"。
