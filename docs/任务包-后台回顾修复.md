# 任务包：后台自动回顾（Background Review）修复

> **项目**: dsh-napcat-bridge  
> **版本**: v0.2.0 (开源发布前)  
> **日期**: 2026-09-05  
> **优先级**: P0 — 阻塞开源发布  
> **参考项目**: `~/dsh-archive-manager`（session 物理删除参照）

---

## 1. 背景

dsh-napcat-bridge 有一个两层记忆体系：**Session 记忆**（群聊规则）+ **用户画像**（个人偏好），通过 `read_memory` / `append_memory` / `update_memory` 三个工具操作，Markdown 文件存储。

其中有一套**后台自动回顾机制**（`BackgroundReviewManager`），设计意图是：每当一个 peer（群聊/私聊）完成一定轮次的对话后，自动 fork 一个 review agent，审视对话内容，提炼有价值的记忆写入文件。

**现状：这套机制从未成功触发过有效回顾——review agent 每次都返回 "Nothing to save"。**

---

## 2. 根因分析（已确认）

### Bug 1（致命）：对话历史永远为空

**文件**: `src/memory/index.ts:172-194`

```ts
const history: HistoryMessage[] = [];
if (Array.isArray(session.history)) {
  history.push(...session.history);
} else if (Array.isArray(session.messages)) {
  history.push(...session.messages);
} else if (Array.isArray(session.events)) { ... }
```

**问题**: DSH session 对象上没有 `history`、`messages`、`events` 这三个字段。对话历史存在 session log 文件里（`~/.dsh/sessions/<workspace>/<sid>/session.jsonl.zstd`），不在 session 对象上。

**结果**: `history` 永远是 `[]`，传给 review agent 的 prompt 里对话内容为空。

### Bug 2（致命）：Review Agent 收到空 prompt

**文件**: `src/memory/review.ts:328`

```ts
const prompt = `${MEMORY_REVIEW_PROMPT_TEMPLATE}\n\n## Current Conversation History:\n${JSON.stringify(history, null, 2)}`;
```

history 为 `[]`，prompt 末尾是 `[]`，模型合理反应就是 "Nothing to save."。

### Bug 3（中等）：Tool call 计数大概率永远为 0

**文件**: `src/memory/index.ts:165-170`

```ts
if (typeof event.data?.toolCallsCount === 'number') {
  toolCallsCount = event.data.toolCallsCount;
} else if (Array.isArray(event.data?.tool_calls)) {
  toolCallsCount = event.data.tool_calls.length;
}
```

**问题**: DSH 的 `turn/end` 事件结构未必包含 `toolCallsCount` 或 `tool_calls` 字段。两个都不存在时 `toolCallsCount` 为 0，tool calls 门控永远不触发，只能靠 turns 门控（10 轮）。

### Bug 4（低）：Review Session 文件堆积

如果 review session 没有被清理，会在 `~/.dsh/sessions/` 下积累无用的 session 文件。

---

## 3. 修复设计（已拍板）

### 3.1 Review Agent 创建方式

**改用 DSH 原生 session fork 机制**：

- 从主 session 的最后一条消息 fork 出新 session
- Review agent 在独立 session 中运行，不污染主 session 历史
- Review agent 自动继承主 session 的完整对话历史（DSH 原生 fork 行为）
- 如果继承的历史不够，`read_chat_history` 工具作为兜底

**Prompt 不需要指示 review agent "先 fork 继承历史"**——因为 DSH 原生 fork 已经让 review agent 拿到了所有历史。Prompt 只需在必要时指示使用 `read_chat_history` 补充。

### 3.2 工具白名单扩展

**文件**: `src/memory/review.ts`

```ts
// 当前
const ALLOWED_MEMORY_REVIEW_TOOLS = ['read_memory', 'append_memory', 'update_memory'];

// 改为
const ALLOWED_MEMORY_REVIEW_TOOLS = ['read_memory', 'append_memory', 'update_memory', 'read_chat_history'];
```

### 3.3 用完即焚：Session 物理删除

Review session 完成后，物理删除其 session 文件，不在 Web UI 留痕。

**参照 `~/dsh-archive-manager/src/workspace.js` 的 `deleteSessionCore` 方法**，核心操作链路：

```
1. sessions.flush(live)                    — 持久化屏障
2. sessions.detachEntered(entry)           — 从实时会话分离
3. projCache?.delete(sessionId)            — 清投影缓存
4. cleanSpill(sessionId)                   — 清 spill 目录
5. removeTranscriptDirectory(sessionId)    — rm 物理文件
6. removeFromWorkspaceAccounts(sessionId)  — 清工作区记账
7. forgetIndexedSession(sessionId)         — 清内存索引 + 墓碑
```

**注意**: `dsh-archive-manager` 依赖 `sessionPersistence.locate(header)` 定位物理路径。实现 agent 需要在 DSH node_modules 中确认这个 API 的可用性。如果 `sessionPersistence` 不可直接访问，可以退而求其次用 `sessionDir` from `@deepseek-ai/dsh-spill-local` 或直接推导路径（`~/.dsh/sessions/<workspace>/<sessionId>/`）。

### 3.4 Tool Call 计数修复

**方案**: 从 `session.snapshotEvents()` 数 `tool/call` 事件，替代不可靠的 `event.data.toolCallsCount`。

在 `turn/end` 事件处理中，从 session 的 events 里统计从上次 `turn/start` 到当前 `turn/end` 之间的 `tool/call` 事件数量。

### 3.5 Session 编号回退修复（顺带）

**问题**: `SessionManager.peerToSessionId()` 编号逻辑不因物理删除而收缩。

**修复**: 在 `peerToSessionId()` 扫描已知 session 时，加物理存在性校验——发现 session 文件不存在就从索引/DB 中清除。

**需要确认**: `workspaceRegistry.headers` 是否可通过编程方式移除单个 header（`delete`/`remove` 方法？），或者需要参照 `dsh-archive-manager` 的 `forgetIndexedSession` 自行实现墓碑机制。
