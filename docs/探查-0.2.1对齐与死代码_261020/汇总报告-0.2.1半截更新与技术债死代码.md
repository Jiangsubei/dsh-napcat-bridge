# dsh-napcat-bridge：DSH 0.2.1 半截更新核查 · 技术债与死代码总表

> 调查日期：2026-10-20  
> 调查方式：6 个只读子代理按模块并行探查 + 主代理交叉抽检（npm 拉取 `0.2.1-rc.2` 真实包核对类型/事件/资源契约）  
> 基线：DSH `0.1.5-rc.1` ──▶ 目标 `0.2.1-rc.2`  
> 结论口径：**A 类 = 半截更新（未完全对齐 0.2.1）**；**B 类 = 技术债**；**C 类 = 死代码**。P0 会导致 0.2.1 下装不上/不可用/崩溃，P1 为规范不符或显著隐患，P2 为清洁度问题。

## 0. 一页结论

**这个仓库目前处于「按 0.2.1 写法改了源码与声明，但没有在 0.2.1 上编译、测试、装配、验证过」的半截状态。** 最关键的三条：

1. **依赖是假的 0.2.1**：`engines.dsh >=0.2.0`、`peerDependencies ^0.2.0`，但 `devDependencies` 与 `node_modules` 实际全是 `0.1.5-rc.1`；`pnpm typecheck` / `pnpm test` 全绿只证明代码符合 **0.1.5** 类型。
2. **`^0.2.0` 根本装不上**（已决策改为 `>=0.2.0-0`）：npm registry 上 0.2.x **没有正式版**（只有 `0.2.0-rc.1/rc.2`、`0.2.1-alpha.*`、`0.2.1-rc.1/rc.2`），semver 的 `^0.2.0` 不匹配预发布版本 → 用户安装/插件市场解析会直接失败（P0）。
3. **多条 0.2.1 接线实际未生效**：`ctx.on('ready')` / `ctx.on('dispose')` 在 0.2.1 中不存在（app-boot 只扩展 `app-boot/config-reload`，cordis 4.0.5 内置事件无 `ready`）→ 旧配置迁移永不执行、卸载清理永不执行；`src/boot.ts` 还静态 import 了 0.2.1 已删除的 `healProfilesModuleFallback` → boot 辅助路径直接模块解析失败。

同时，交付报告声称已完成的清理有多处**与代码事实不符**（详见 §5），不能作为「已对齐」的依据。
