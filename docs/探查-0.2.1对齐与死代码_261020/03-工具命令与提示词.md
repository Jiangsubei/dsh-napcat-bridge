## 4. 待确认项（无法在本仓库确证）

1. **Q1（`tools.execute` 缺 `callId` 的运行时影响）**：`tests/contract/assembly.test.ts:144-165` 调 `tools.execute({ name, arguments, agent, signal })`，未提供 0.2.1 必填的 `callId`（`.../dsh-tools-0.2.1-rc.2/package/lib/types/index.d.ts:216-217`）。实现里未见 `callId` 校验（`lib/index.js:3230-3242` 直接读取），缺省时事件/日志会带 `undefined`，**是否会触发下游持久化/UI 异常待真机确认**；`tests` 里 `tools` 为 `any`，编译期无保护。
2. **Q2（工具失败表达口径）**：0.2.1 是否官方推荐「抛错 → `isError`」而非 `{success:false}`？已确认实现语义（B3），但未找到官方 agent note/文档明确规定；需在改造前与用户确认全局失败契约，避免只改一半。
3. **Q3（是否接入 `ctx.commands`）**：0.2.1 `dsh-commands` 面向「interactive UI adapters」，处理 UI 发起的斜杠命令；NapCat 的 `/权限` 来自 QQ 文本消息且需管理员白名单门控，语义不同。**不宜直接迁移**，但 `package.json:72` 的依赖声明与零使用需要决策（A2）。
4. **Q4（宿主服务稳定性）**：`sessionController`、`agentDefaultModel`、`tokenMeter`、`sessionProjections` 在本地两侧 `node_modules` 均无公开类型声明，本仓库全部 `as any` 访问。0.2.1 是否为这些服务提供公开/稳定契约，**待查宿主源码或官方文档**；在此之前 B2/B11 的改造需谨慎。
5. **Q5（诊断装配下的提示词注入）**：`src/prompt/dynamic.ts:42-59` 依赖 `assembleCtx.agent` 取 sessionId；若 0.2.1 的诊断装配不带 `agent`（`.../dsh-agent-0.2.1-rc.2/.../runtime-types.d.ts:16` 注明 `absent on diagnostics`），则 `sessionId` 为空 → 跳过「非 QQ 会话返回空」的过滤 → **可能向诊断装配注入人格/行为准则**。是否可接受待确认（当前测试用 `{}` 调用 `assemble()` 时正是这条路径，但断言只看 `napcat:qq_scenario`，未看 `napcat:behavior_persona`，见 B8）。
6. **Q6（`private-file` 的 `busid` 预留）**：注释称「保留为调用上下文与后续 NapCat 版本兼容预留」；若确有计划，应改为显式 TODO 并保留，否则按 C4 删除。

## 5. 结论摘要（≤10 条，按优先级排序）

1. **本模块在 0.2.1 下没有 P0 破坏**：`defineTool`、`tools.register`、`tools.guard`、`systemPrompt.context`、`permissionPresets.{names,current,set}` 在 `0.2.1-rc.2` 中签名与 0.1.5 一致，现有工具/提示词/命令在装配层可继续工作。
2. **A 类唯一硬问题仍是版本半截**（A1）：`peerDependencies` 声明 `^0.2.0`，但 devDeps 与实际安装是 `0.1.5-rc.1`，本模块的 `tsc`/31 项契约测试都只证明了 0.1.5 类型下的正确性。
3. **最高优先修复是 `/模型`·`/思考` 的假成功**（B1）：`safeSyncSessionModel` 吞掉 `selectModel` 异常（`commands/index.ts:101`），调用方仍回「已切换」；0.2.1 会抛 `RemoteError`，用户却看不到失败。
4. **其次是全局猴子补丁**（B2）：临时改写 `agentDefaultModel.saveSelection` 依赖了 0.2.1「不 await 保存默认」的时序，属进程级副作用，建议替换或至少加时序契约测试（现有 mock 与真实语义不符，B7）。
5. **工具失败语义在 0.2.1 下会丢失**（B3）：只有抛错才是 `isError:true`，当前全部 `{success:false}` 会被模型当成成功结果；需先与用户确认统一口径再改。
6. **装配覆盖存在真实缺口**（B4+B5）：测试只认 5 个工具名、只有 `read_chat_history` 走 `tools.execute`；3 个工具（`list_group_files`/`wait_for_user_messages`/`react_message`）与全部 memory 工具未被「呈现侧/执行侧隔离」断言覆盖，且工具名在 4 处魔法字符串重复。
7. **确认死代码 6 处**：`registerQQScenarioDynamicPrompt`（no-op）+ 其零引用别名、`splitMessageText`、3 个过宽导出、`private-file.busid` 死字段、`fetchChatResource` 的 `sender` 死传参、8 个零引用 OneBot 细分类型。其中 no-op 与 `splitMessageText` 各有一条「为死代码续命」的测试（契约 5 / 契约 2）。
8. **提示词测试是无效断言**（B8）：`qq-scenario-dynamic-prompt.test.ts` 用 `{session}`/`{peer}` 传参，但 0.1.5 与 0.2.1 的 `AssembleContext` 都只有 `scope`/`signal`（+`agent`），参数被忽略；契约 4 还访问私有 `layers`，契约 5 只测 no-op。应改为真实 `agent` 装配并删除 no-op 契约。
9. **长等待工具未纳入 0.2.1 超时预算**（B15）：`wait_for_user_messages` 未声明 `timeoutMs`；不声明不会崩（策略对 undefined 放行），但建议显式声明以符合 0.2.x 协作取消规范。
10. **建议的落地顺序**：A1（升级 devDeps 重跑全量验证）→ B1/B2/B7（模型切换正确性）→ B3（失败语义口径确认）→ B4/B5（单一工具名源 + 装配断言）→ C1/C2/C3/C4/C5（死代码清理，同步删两条续命测试）→ B8/B10/B11（测试与结构整理）。
