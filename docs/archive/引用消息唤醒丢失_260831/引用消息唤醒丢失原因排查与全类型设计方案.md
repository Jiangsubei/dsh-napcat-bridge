# 引用消息入站唤醒丢失问题深层原因排查与全类型设计方案

## 1. 现场问题回溯与深层原因剖析

### 1.1 现场日志现象
- **NapCat 原始接收日志**：
  ```
  08-31 11:37:55 [info] BotNickname | 接收 <- 群聊 [🌳🏠温馨树洞小屋🎉加油鸭(3000000001)] [你醒了？你被基米单杀了(2000000001)] [回复消息 [用户名加载中…(1617307295)] [图片]] @BotNickname (1000000001) 说的这个图
  ```
- **实际发给 Agent 的唤醒 Prompt**：
  ```
  [QQ群聊: 3000000001] [2026-08-31 11:37:55] 发送者: 你醒了？你被基米单杀了 (QQ: 2000000001)
  @BotNickname(1000000001) 说的这个图
  ```
- **缺失内容**：
  引用回复的上下文 `[引用回复 用户名(1617307295): "[图片:.../xxx.jpg]"]` 完全缺失，且被引用的图片未注入视觉通道，导致大模型完全无法得知用户“说的这个图”指的是哪张图。

---

### 1.2 深层根因定位（共 4 个关键断点）

#### 断点 1：`shouldWakeup` 门控逻辑分支割裂，非纯引用分支漏传 `quoted`
在 `src/gateway/wakeup.ts` 的 `shouldWakeup` 实现中：
- 当用户发出的消息同时包含 `@机器人` 和 `reply` 时，代码首先在 **3.2 (1) @机器人分支** 命中：
  ```typescript
  // (1) @ 机器人
  if (botQQ && atQQs.includes(botQQ)) {
    const payload: WakeupPayload = {
      trigger: 'at',
      peer,
      from_user: fromUser,
      from_name: fromName,
      content,
      images: images.length > 0 ? images : undefined,
      timestamp,
      // ❌ 此处完全没有解析或携带 quoted 字段！
    };
    return { wakeup: true, trigger: 'at', payload };
  }
  ```
- 同理，**3.1（私聊消息）** 与 **3.2 (3)（点名昵称/别名唤醒）** 构造 `WakeupPayload` 时，也完全没有装配 `quoted` 字段；
- 只有在 **3.2 (2)（纯引用机器人唤醒）** 且用户**没有 @ 机器人**时，才尝试提取了 `quoted`。一旦用户既引用又 @机器人，或者引用的是他人消息再 @机器人，`quoted` 必定 100% 丢失。

#### 断点 2：引用的若是他人消息（非 Bot 自身），判定为非纯引用唤醒后元数据丢失
- 在 `(2) 引用回复机器人` 中，原逻辑检查 `quotedMsg.user_id === botQQ`；
- 如果群友 A 引用群友 B 的图片并 @BotNickname，被引用者不是 Bot，故 `(2)` 判定不成立；随后流入 `(1) @机器人`，再次因为断点 1 丢失引用内容。

#### 断点 3：缺乏 OneBot 11 `get_msg` API 兜底拉取机制
- 当前 `getQuotedMessage` 仅查询本地 SQLite 数据库（`db.getMessage(replyId)`）；
- 若被引用的消息是机器人启动前的历史消息，或入库前遗漏的消息，本地数据库查询为 `null`；
- 缺少调用 NapCat 的 `get_msg` API 实时反查机制与本地补齐入库逻辑。

#### 断点 4：多模态图片未向下游打通
- 当被引用的消息是一张图片或包含图片（`quotedMsg.local_path` 或 `images`）时，当前仅将其作为文本拼接 `[图片:xxx]`，未将图片路径合并到唤醒包的 `images` 列表中，导致视觉大模型只能看到文字路径而看不到实际画面。

## 2. 被引用消息全量类型盘点与归一化设计

在 QQ / OneBot 11 (NapCat) 体系中，被引用的消息（Quoted Message）共有 **14 种主要类型与场景**，归一化规范如下：

| 序号 | 消息类型 | OneBot 11 原始消息段结构 | `quoted.text` 归一化表达 | 多模态 / 视觉联动 |
|---|---|---|---|---|
| 1 | **纯文本** | `[{ type: 'text', data: { text: '文本' } }]` | `"文本"` | 无 |
| 2 | **包含 @ 的文本** | `[{ type: 'at', data: { qq: '123' } }, { type: 'text', data: { text: '你好' } }]` | `"@张三(123) 你好"`（通过 `resolveAtNicknames` 归一化） | 无 |
| 3 | **图片消息**（现场场景） | `[{ type: 'image', data: { local_path: '/path/a.jpg', file: 'a.jpg' } }]` | `"[图片:/path/a.jpg]"` | **将图片 localPath 追加至唤醒包 `images`**，使 Agent 多模态视觉可感知 |
| 4 | **表情包 / 动画表情** | `[{ type: 'image', data: { sub_type: 1, summary: '[动画表情]', local_path: '...' } }]` | `"[表情包:[动画表情] 已保存: /path/f.gif]"` | 同普通图片 |
| 5 | **文件消息** | `[{ type: 'file', data: { file_name: 'a.pdf', local_path: '...' } }]` | `"[文件:a.pdf 已保存: /path/a.pdf]"` 或 `"[群文件:a.pdf (ID:xxx)]"` | 提供文件名及本地路径 |
| 6 | **合并转发** | `[{ type: 'forward', data: { id: 'xxx' } }]` | `"[合并转发 (ID:xxx)]"` | 标明转发容器 ID |
| 7 | **语音消息** | `[{ type: 'record', data: { ... } }]` | `"[语音]"` | 标注为语音 |
| 8 | **视频消息** | `[{ type: 'video', data: { ... } }]` | `"[视频]"` | 标注为视频 |
| 9 | **卡片 / 小程序 / 分享** | `[{ type: 'json' / 'xml' / 'share' / 'lightapp', data: { ... } }]` | `"[卡片消息:标题]"`、`"[位置:深圳湾]"`、`"[分享:小程序名]"` 等 | 提取关键摘要 |
| 10 | **戳一戳 / 抖动** | `[{ type: 'poke' / 'shake' }]` | `"[戳一戳]"` / `"[窗口抖动]"` | 标注动作 |
| 11 | **复合富媒体** | 文本 + 图片 + @ 混合 | `"文本 @张三(123) [图片:/path/a.jpg]"` | 文本完整拼装 + 图片联动 |
| 12 | **嵌套引用消息** | 包含 `reply` 段的被引用消息 | 去除其内部嵌套的 `reply` 标记，保留真实主体内容 | 防止 CQ 码嵌套污染 |
| 13 | **已撤回消息** | 本地标记 `recalled: 1` 的消息 | `"〔已撤回〕"` 或 `"〔已撤回内容: ...〕"` | 提示该内容已被撤回 |
| 14 | **历史过期/未知消息** | 本地未查到且 `get_msg` API 失败 | `"[历史引用消息 ID:12345 (内容已过期或无法获取)]"` | 优雅保底，绝不丢引用头 |

## 3. 详细设计方案

### 3.1 引用提取与装配架构（全触发方式解耦）
将 `quoted` 解析与具体的唤醒判定触发器（direct / at / quote / mention）解耦：

```
[入站消息事件]
       │
       ▼
1. 基础解析 (parseNormalizedContent) -> 提取 replyId, content, atQQs, images
       │
       ▼
2. 异步引用解析 (resolveQuotedInfo)
   - 若 replyId 存在:
     a. 先查本地 DB (db.getMessage(replyId))
     b. 若本地未命中，调用 GatewayServer get_msg(replyId) -> 归一化并回填 DB
     c. 解析被引用者名称 (结合 sender_name / resolveNickname)
     d. 组装 quoted 对象: { msg_id, user_id, from_name, text, images }
       │
       ▼
3. 统一门控判定 (shouldWakeup)
   - 无论命中了 私聊 / @机器人 / 引用机器人 / 点名唤醒：
     只要存在 quoted，一律将其注入 payload.quoted！
   - 若被引用消息包含图片，合并到 payload.images（去重保持顺序）。
```

### 3.2 本地 SQLite 优先 + NapCat API 二级兜底 + 三级优雅降级策略

为了避免对 NapCat 发起不必要的 API 调用，同时确保在历史消息或重启遗漏场景下依然具备强大的恢复能力，系统采用 **三级阶梯式引用解析策略**：

1. **第一级：本地 SQLite 数据库极速命中（本地优先，耗时 < 1ms，0 网络/API 开销）**
   - 优先通过 `db.getMessage(replyId)` 检索本地落库记录。
   - 只要是桥接在线期间产生的消息（包括刚刚发送的图片、文字、文件等），直接从本地毫秒级获取，完全不打扰 NapCat。

2. **第二级：NapCat `get_msg` API 异步拉取 + 自动回填入库（二级兜底）**
   - 当本地 SQLite 查询为 `null` 时（如：机器人刚刚启动，被引用的消息发生在启动前）：
   - 调用 NapCat OneBot 11 Action：`server.getMsg(replyId)`。
   - 经实证，NapCat 支持 `get_msg`（入参 `{ message_id: replyId }`），只要该消息仍驻留在 NTQQ 客户端缓存中即可成功拉取；
   - 拉取成功后，系统自动解析并执行 `db.saveMessage(...)` 回填至本地 SQLite，实现历史消息“查一次、存本地、后序免查”的自愈能力。

3. **第三级：拉取不到/过期/失败时的优雅降级（三级保底，绝不断链）**
   - **边界场景**：若消息时间极其久远被 NTQQ 客户端彻底清理，或者 `message_id` 不存在，NapCat `get_msg` 会返回失败或超时抛错；
   - **优雅降级处理**：
     - 系统捕获异常并不中断唤醒流程；
     - 构造占位 `quoted`：
       ```typescript
       quoted = {
         msg_id: replyId,
         user_id: '',
         from_name: '',
         text: '〔历史引用消息：内容已过期或无法获取〕',
       };
       ```
     - 最终在 Prompt 中呈现为：
       `[引用回复 消息ID: 12345: "〔历史引用消息：内容已过期或无法获取〕"]`
     - **作用**：大模型依然能明确知道用户**刚才做了引用回复动作**，而非把引用的指代性提问（如“这个图怎么样”、“上面说的对吗”）误当成无由头的胡乱发问，大模型可以精准回应“你引用的历史消息时间较久已无法查看，请问具体是关于什么的？”。

---

### 3.3 GatewayServer 新增 `getMsg` Action 支持
在 `src/gateway/server.ts` 中新增：
```typescript
async getMsg(messageId: number | string): Promise<OneBotActionResponse> {
  return this.sendAction('get_msg', {
    message_id: Number(messageId),
  });
}
```

---

### 3.4 唤醒提示词渲染规范 (`formatWakeupPrompt`)
格式统一为：
```
[QQ群聊: 3000000001] [2026-08-31 11:37:55] 发送者: 你醒了？你被基米单杀了 (QQ: 2000000001)
[引用回复 用户名加载中… (QQ: 1617307295): "[图片:/dsh/workspace/napcat_download/image/common/abc.jpg]"]
@BotNickname(1000000001) 说的这个图
```
- 若没有获取到昵称，优雅显示 `[引用回复 QQ: 1617307295: "..."]`；
- 若获取到昵称，显示 `[引用回复 昵称 (QQ: 1617307295): "..."]`；
- 若被引用者是 Bot 自身，显示 `[引用回复 机器人昵称 (QQ: bot_qq): "..."]`；
- 若拉取失败，显示 `[引用回复 消息ID: 12345: "〔历史引用消息：内容已过期或无法获取〕"]`。

## 4. 实施与契约测试计划

1. **契约测试先行（TDD）**：
   - 增加契约：群聊中「@机器人 + 引用回复」必须 100% 带出 `payload.quoted`；
   - 增加契约：群聊中「点名机器人 + 引用回复」必须 100% 带出 `payload.quoted`；
   - 增加契约：私聊中「引用历史消息」必须 100% 带出 `payload.quoted`；
   - 增加契约：引用回复包含图片时，图片本地路径必须注入唤醒包并在 `images` 中可感知；
   - 增加契约：本地 DB 查无记录时，通过 `getQuotedMessage`（调用 `get_msg`）拉取、解析并回填 DB；
   - 增加契约：本地 DB 和 `get_msg` 双失败时，优雅降级为保留引用头与占位提示。
2. **代码修改清单**：
   - `src/gateway/server.ts`: 新增 `getMsg` 方法
   - `src/gateway/wakeup.ts`: 统一 `quoted` 解析逻辑，覆盖所有唤醒分支，支持图片合并与降级占位
   - `src/gateway/session.ts`: 优化 `formatWakeupPrompt` 渲染规范
   - `src/index.ts`: 接入 `db.getMessage` + `server.getMsg` 双层兜底解析
3. **构建与真机对齐**：
   - 执行 `pnpm test` 验证全量契约测试；
   - 执行 `pnpm build` 重新编译产物至 `dist/`，确保生产路径完全生效。
