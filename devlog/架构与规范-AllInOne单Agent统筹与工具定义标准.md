# 架构演进与工具规范：All-in-One 单 Agent 统筹与工具定义设计标准

> **文档定位**：系统演进设计草案与工具工程设计准则  
> **创建日期**：2026-10-26  
> **关联模块**：`src/tools/`, `src/memory/`, `src/gateway/session/`, `src/prompt/`

---

## 1. 架构演进远景：从分散 Background Agent 走向 All-in-One

### 1.1 现状与痛点剖析
当前系统中，除了处理实时聊天的主会话 Agent 外，系统为了完成异步维护任务，引入了多个独立的 **Background Agent**（如表情包整理 Curator、记忆归纳 Background Review）：
1. **架构与调度沉重**：每个 Background Agent 均需要独立的 Fork 会话、白名单沙箱配置、防重入锁机制、独立的定时器与错峰倒计时管理；
2. **上下文人为割裂**：后台 Agent 缺乏主会话中生动、实时的聊天情绪与互动语境，只能事后通过数据库反查零碎线索；
3. **系统复杂性攀升**：随着功能增多（如好友管理、群管理、资源巡检），后台 Agent 数量容易膨胀，维护成本倍增。

### 1.2 All-in-One 核心理念与因果关系
**最终目标**：去除所有零散的 Background Agent，由 **单一 Agent（All-in-One）统筹管理一切事物**（即时互动 + 后台顺手维护）。

为支撑该架构，核心因果设计如下：
- **`send_qq_message` 工具的必要回归**：
  - 在传统的“回合终答直发”模式中，出站消息必须等到 Agent 回合完全结束才能发出，导致如果 Agent 想在发完消息后整理数据，用户就必须忍受漫长的响应延迟；
  - **核心解耦**：引入 `send_qq_message` 工具，使“向 QQ 发送答复”与“Agent 回合结束”彻底解耦；
  - **执行流闭环**：
    1. 用户发来消息，Agent 进行推理；
    2. Agent 调用 `send_qq_message` 将文本即时推送到 QQ（用户端秒级收到回复，体验零感知延迟）；
    3. **消息发出后回合不立刻结束**，Agent 自然进入“顺手维护期”：
       - 若刚才聊到了新梗或好玩的新图，顺手调用 `collect_face` 入库；
       - 若对话中用户表达了持久偏好或群规变动，顺手调用 `create_memory` / `edit_memory` 沉淀；
       - 若表情包库超过了预算配额，顺手调用表情管理工具进行清理；
    4. 所有顺手事务处理完毕，模型不再发起工具调用，回合自然平稳终结。

### 1.3 关键配套拼图：表情工具解耦与表情管理工具提前至 P1
在表情包体系与未来 All-in-One 模式下，工具职责必须清晰解耦：
- **`collect_face` 纯净化**：职责单一只做“收录入库”（从当前消息或指定图收藏），不再混杂“传 face_id 变成补标/改标”的模式重载；
- **独立研发 `manage_faces`（表情管理工具）**：专职负责表情库生命周期治理（补充/修改标签、按 ID 删除表情、查询配额占用、淘汰冷门表情）；
- **排期升级至 P1**：由于没有管理工具，表情库达到配额后 Agent 无法自愈与整理，因此 `manage_faces` 直接提升至 **P1**，与预设和工具规范化一起研发落地。

## 2. 预设与工具的分工哲学

预设（Preset）与工具定义（Tool Definition）必须权责分明，坚决杜绝职责混淆：

```
┌────────────────────────────────────────────────────────┐
│ 预设系统 (Preset / System Prompt)                      │
│ - 职责：宏观定调（Macro Identity & Scene）             │
│ - 范围：声明当前处于 QQ 聊天场景、拟人风格、排版禁忌   │
│ - 边界：坚决不把各工具的微观调用逻辑塞入预设           │
└──────────────────────────┬─────────────────────────────┘
                           │ 宏观上下文约束
                           ▼
┌────────────────────────────────────────────────────────┐
│ 工具定义 (Tool Definition)                             │
│ - 职责：微观决策（Micro Decision & When to Use）       │
│ - 范围：明确声明工具能做什么、何时用、何时不用         │
│ - 边界：自包含决策边界，模型按需自发调用               │
└────────────────────────────────────────────────────────┘
```

1. **预设定场景与行为大方向**：
   - 负责设定整体人设（Persona）与社交准则（Behavior）；
   - 通过 `tools.restrict` 白名单物理拦截宿主高危工具（`bash`, `pwsh`, `write_file` 等）；
   - 通过 `systemPrompt.section({ complete: true })` 彻底剔除宿主软件工程 Coding 提示词。
2. **工具定义定决策契机与执行边界**：
   - 如果把具体工具的调用细节全部堆在 System Prompt 中，会导致 System Prompt 剧烈膨胀、挤占 Context 预算、破坏静态 Cache，并容易引发大模型注意力稀释与规则冲突；
   - 工具应该具有“自治说明性”，通过规范精练的描述，让模型在面对工具集时能够精准感知每个工具的触发契机。

## 3. 工具定义设计铁律（Tool Definition Standards）

为确保全项目工具既能被模型准确理解，又能实现超低 Token 消耗，制定以下四条设计铁律：

### 3.1 分级模式（拒绝机械小作文）
工具定义不搞一刀切的长篇模板，根据工具的复杂度和混淆度实行分级：
- **简单直观型工具**：一句话自然融入使用契机（如使用 `when you need...`、`用于...时`）；
- **复杂/易混淆型工具**：分句显式写明核心功能、适用场景（`Use it when...`）以及排除场景（`not for...`）。

### 3.2 参数自解释（Parameters 隐含 How to use）
- 工具的 `description` 只需要阐明**“它能做什么、什么时候用、什么时候不用（Why & When）”**；
- 参数列表（`parameters schema`）天然就是结构化的**“操作指南（How to use）”**；
- 主描述中**严禁啰嗦教大模型如何传参、如何调接口**，坚决去除冗余流水账，保持描述纯粹聚焦在时机与边界上。

### 3.3 极致精炼与 Token 预算敏感
- 工具定义是每一次请求大模型时常驻系统上下文的固定开销；
- 工具描述越冗长，多工具同时挂载时上下文膨胀越严重，注意力越容易涣散；
- 坚持高信息密度、精简有力的短句表达，既提升模型注意力对齐度，又极致降低 Token 消耗。

### 3.4 滥用排他原则（When not to use 的本质是意图防混淆）
- **重新定义“滥用”**：滥用不是指模型调用频繁（如果针对场景 B，模型用工具 B 完成了任务，频率再高也是好工具）；滥用是指**意图混淆（Semantic Confusion / Misrouting）**——用户明明提出了需求 A，模型却误调了原本针对需求 B 的工具 X；
- **排他设计**：`When not to use` 仅用于**高危混淆区域**，明确告知模型“此工具并非用于处理需求 A”，阻断错误路由，指引模型去使用正确工具。

### 3.5 消除“恐吓式词汇”与寒蝉效应
- 现代对齐大模型（经过强化学习与安全对齐）本身已具备极强的克制力；
- 避免在工具描述中过度使用“切勿骚扰”、“严禁”等负面恐吓词，防止模型产生过度克制的寒蝉效应（甚至在用户主动开玩笑要求互动时也不敢调用）；采用中性、场景化的正向引导即可。

### 3.6 代码运行时拦截替代提示词防御
- 软件工程铁律：运行时代码能校验保障的事情，绝不把焦虑全部转嫁到提示词上；
- 例如对于不存在的 ID（如不存在的 `face_id`），由工具底层直接返回清晰的报错引导模型重试或查询，而无需在描述中声嘶力竭地写“严禁凭空编造不存在的 ID”。

### 3.7 参数精简与无用参数剔除
- 能够由底层根据输入（如后缀名）高确定性自动推导的参数，应当彻底隐藏或移除（如 `send_file` 中多余的 `file_type`，纯靠 `file_path` 即可）；
- 实际场景中不需要的参数果断砍掉（如 `list_faces` 中的 `cursor` 分页游标，实测 100 张上限无需复杂翻页），降低模型的参数决策负担。
