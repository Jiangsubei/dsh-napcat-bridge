# 排查记录：Bot 自身出站消息未落库（2026-11-04）

## 1. 现象

- 用户入站消息在 `messages.sqlite` 中持续正常写入；
- Bot 通过 `send_qq_message` / `send_private_msg` / `send_group_msg` 发出的消息，在 QQ 端可见，但本地 `messages` 表中没有对应 `self = 1` 记录；
- 表现为 `read_chat_history` 的 `self_only` 查询结果为空，Agent 无法回溯"自己说过什么"；
- 用户怀疑与当日未推送的 Agent IPC 提交有关。

## 2. 关键数据证据（均已脱敏）

### 2.1 自身消息时间分布

按小时聚合 `messages` 表（脱敏 ID：私聊用户 `1000000001`、群 `8000000001`）：

| 时间 | 入站条数 | 自身条数 |
|---|---|---|
| 11-04 22 | 37 | **0** |
| 11-04 21 | 1 | **0** |
| 11-04 20 | 6 | **0** |
| ... | ... | ... |
| 11-04 10 | 51 | **1** |

11-04 全天仅 1 条 `self = 1`。

### 2.2 配置改动的时间断点

SnowLuma 的 OneBot 配置 `config/onebot_<botQQ>.json` 最后修改时间为 **11-03 21:02:14**，其中：

```json
"wsClients": [
  {
    "name": "dsh",
    "reportSelfMessage": false,
    ...
  }
]
```

即：连接 dsh 的 WebSocket 客户端被设置为**不再上报自身消息**。

### 2.3 断点后的唯一两条自身记录，全部被引用过

统计 `self = 1 AND time >= 11-03 21:02:14`，结果只有 2 条：

| 时间 | 会话 | msg_id | 是否被其它消息引用 |
|---|---|---|---|
| 11-03 23:01:34 | group_8000000001 | 263831662 | **是（quotedBy = 1）** |
| 11-04 10:13:20 | group_8000000002 | -1494686739 | **是（quotedBy = 1）** |

这两条恰好命中了 `index.ts` 中"引用消息本地未命中 → `get_msg` 拉取 → `saveMessage` 回填"的分支（`index.ts` 第 913-953 行），其 `time` 取的是远端消息时间，因此看起来"像是当时实时写入"。

断点前的自身消息（如 11-03 19:46 私聊那条）没有被任何消息引用，属于真实实时落库。

## 3. 日志证据（SnowLuma，已脱敏）

SnowLuma 侧持续产生 `[自身]` 事件，但 dsh 插件侧只有入站消息入库：

```
10:13:18 [Bridge.Action] send_group_msg params=group_id=8000000002 message=[len=2]
10:13:19 [OneBot] 群聊 8000000002 | 发送：...
10:13:19 [Event] [自身] 群 [...] | [bot(1000000000)]: ID:-1494686739 ...
```

`[自身]` 事件在 SnowLuma 内部存在，但由于 `reportSelfMessage = false`，该事件不会被推送到 dsh 的 WebSocket 客户端；插件因此收不到 `post_type === "message_sent"` 的消息事件，`index.ts` 中的落库分支自然不会执行。

## 4. 根因

1. **直接根因**：SnowLuma/NapCat 的 `reportSelfMessage` 被关闭，自身消息不再通过 OneBot 事件上报给 dsh。
2. **设计缺陷**：插件没有任何"出站成功后主动落库"的逻辑，`messages` 表的 `self = 1` 记录完全依赖外部事件上报。一旦对端关闭上报开关，出站历史就会静默丢失。
3. **断点表现为"今天某次重启后失效"**：配置虽在 11-03 21:02 写入文件，但通常在下一次 QQ/NapCat 或连接重载后才真正生效，因此故障在今日白天才暴露。

## 5. 排除项：与 Agent IPC 的关系

- `send_agent_message` 属于进程内 Agent 通信，本就不产生 QQ 消息事件，也不应写入 QQ 聊天历史；
- 检查 SnowLuma 日志，Agent IPC 测试期间 `send_group_msg` / `send_private_msg` 的 `group_id` / `user_id` 参数均正确，消息实际送达了正确的 QQ 会话；
- 出站落库路径与 `send_qq_message` 的 `ctx.peer` 解析无关，而是由 NapCat 上报事件驱动；
- 因此本次自身消息缺失**不是** Agent IPC 提交引入的回归，IPC 提交也未被证实与落库链路存在耦合。

> 注：`send_qq_message` 当前从 `exec.agent.session.id` 取真实会话 ID，发送目标解析正确（日志可见）。

## 6. 修复候选方案

### 方案 A：环境侧恢复上报（临时、零代码）

在 SnowLuma / NapCat 面板中为 dsh 的 WebSocket 客户端开启"上报自身消息"（`reportSelfMessage: true`）。

- 优点：改动最小，立即恢复历史落库；
- 缺点：依赖用户环境配置，重装/重配后易再次丢失；且自身消息事件回流可能触发不必要的唤醒判定，需要确认现有自循环防护能正确拦下。

### 方案 B：出站成功后主动落库（推荐根治）

在出站发送收口处（`NapCatGatewayServer.sendAction` 的 `send_group_msg` / `send_private_msg` / `send_msg`，或各发送工具的 execute 内）于发送成功后写入 `messages` 表：

- `peer`：目标会话；
- `msg_id`：`res.data.message_id`；
- `user_id`：`bot_qq`；
- `sender_name`：`aliases[0]`；
- `self`：1；
- `content` / `raw`：归一化后的消息段；
- 使用 `saveMessageIfNotExists` 或 `INSERT OR REPLACE` 保证与可能的上报事件幂等。

覆盖范围需明确：`send_qq_message`（含多段拆分）、`send_file`、`send_face`、`ask_user_question`、审批通知、斜杠命令回复、定时/主动唤醒消息。

- 优点：不依赖对端配置，从根上避免静默丢失；
- 缺点：需要统一处理文本/图片/文件/表情的消息段归一化与多段 `message_id`，工作量与回归面较大。

## 7. 当前状态

- 已按用户拍板（判据 = 发送成功即落库；全部出站统一收口）落地修复；
- 修复实现与验证见下节。

## 8. 修复落地（方案 B：发送成功即主动落库）

### 8.1 判据

以 OneBot Action 应答为准，**不依赖 `reportSelfMessage`**：

- `send_group_msg` / `send_private_msg` / `send_msg` 应答满足 `status === 'ok' || retcode === 0`；
- 且 `data.message_id` 为**非零安全整数**（群聊 ID 可能为负，保留负号）；
- 两者同时成立才落库；失败、超时、缺 `message_id` 一律不落库（无主键的记录无法被引用/撤回寻址）。

### 8.2 统一收口位置

在 `NapCatGatewayServer.sendAction` 内统一拦截上述三个 action 的成功应答，通过
`options.onMessageSent` 回调上报 `{ action, peer, msgId, message, time }`。
所有出站通道（`send_qq_message`、`send_file`、`send_face`、提问卡片、审批通知、斜杠命令回复、
定时/主动唤醒）最终都经由 `sendAction`，因此**无遗漏、无需逐个工具改造**。

插件侧在 `db.init()` 之后注入该回调，落库逻辑独立在 `src/outbound/self-record.ts`：

- `normalizeOutboundSegments`：纯文本 / 消息段数组统一归一化；
- `parseNormalizedContent`：复用入站同一套内容归一化（文本、@、引用、图片、表情包、文件、卡片）；
- `inferOutboundMessageType`：与入站口径一致的 dominant type（text / image / sticker / file / group_file / reply ...）；
- `saveMessageIfNotExists`：与未来开启 `reportSelfMessage` 后回流的事件幂等，不重复、不覆盖。

`peer` 解析：`send_group_msg` → `group_<group_id>`；`send_private_msg` → `user_<user_id>`；
`send_msg` 按 `group_id` 优先、`user_id` 兜底。`time` 取发送完成时刻（毫秒）。
`sender_name` 与历史自身消息口径一致：`bot_nickname || aliases[0] || '智能助手'`。

### 8.3 验证

- `tests/contract/outbound-self-record.test.ts`（14 项）：
  - 纯函数：文本 / 引用+@ / 图片+表情包 / 空内容 / 字段无 undefined / 群文件与私聊文件类型；
  - 真实 WS 网关 + 真实 SQLite 闭环：群聊成功、私聊成功、retcode 失败不落库、缺 `message_id` 不落库、
    `send_msg` peer 解析、重复上报幂等；
  - **真实装配闭环**：`bootDshNapcatBridge` 挂载后断言 `onMessageSent` 已接线，并通过真实 WS 客户端
    发送成功，从插件真实数据库文件中读出 `self = 1` 记录（`msg_id / peer / user_id / sender_name / content / type`）。
- 回归：`gateway-actions`、`private-self-message`、`send-message-tool`、`send-file`、`recall-message`、
  `read-chat-history-peer`、`assembly`、`aside-suppression-and-fallback`、`negative-msg-id`、
  `outbound-stream`、`send-message-quote`、`quote-assembly` 全部通过；`pnpm typecheck`、`pnpm build` 通过。

### 8.4 运维提示

- 无需修改 SnowLuma 配置；如用户后续手动开启 `reportSelfMessage`，事件回流与主动落库互为幂等，不会产生重复记录；
- 插件升级后需重启 DSH（`main → dist/`），否则仍跑旧构建。
