# 多通道独立运行时快照注入架构设计与落地清单

- **日期**：2026-11-08
- **责任模块**：`src/prompt/`、`src/index.ts`、`src/memory/`、`src/slang/`
- **目标**：将原本统一揉入 `systemPrompt.context` 的单一巨型运行时快照（Runtime Context Snapshot），改造为基于 `agent/pre-step` 瀑布流的**多通道独立快照（Multi-Channel Independent Snapshots）**。不同模块（黑话、表情包、人格设定、行为准则、长程记忆与规则、用户画像）各自拥有独立脏检查、独立 Projection 与生命周期，发生变动时仅追加所属通道的独立快照，避免大体积资产重复重发，在多轮交互中节省 70%~90% 上下文 Token。

---

## 1. 背景与根因剖析

### 1.1 现状与瓶颈
1. 在原有架构中，`SnapshotManager` / `setupSnapshotHub` 将 `napcat:memory`、`napcat:slang`、`napcat:face_summary`、`napcat:behavior_persona` 统一注册到 DSH 的 `systemPrompt.context(...)`；
2. DSH 官方底层（`dsh-system-prompt` 与 `dsh-agent-loop`）对于 `systemPrompt.context` 的设计是：
   - 在每个 step 前，通过 `joinContextSections()` 将所有注册的 context 字符串强行换行拼接为一整个大文本；
   - 开头固定添加：`Current runtime context. This snapshot supersedes earlier runtime-context snapshots.\n\n`；
   - DSH 内部的 `RuntimeContextProjection` 仅保留单一状态槽 `this.retained.text`；
3. **致命后果**：
   - 表情包库存与黑话库体积巨大（几千到上万字），但内容极少变动；
   - 记忆与用户画像体积小，但会话中更新频繁；
   - 只要任何细微变动（如记了一条新喜好，或群内发言人切换），DSH 就判定整串文本变化，将包含**完整表情包 + 完整黑话 + 完整人格准则 + 记忆**的巨型消息完整再次追加到会话历史中，导致 Token 极速消耗与过早触发上下文压缩。

### 1.2 DSH 原生多快照契约事实查证
- DSH `@deepseek-ai/dsh-llm` 的消息契约中定义了：
  ```typescript
  export type ContextForm = 'instructions' | 'catalog' | 'snapshot' | 'notice' | 'relay' | 'recall';
  ```
  其中 `form: 'snapshot'` 的语义被严格定义为：
  > `Current state, where a later snapshot from the same producer supersedes an earlier one.`
  （同一个 producer 的后继快照仅覆盖该 producer 自身的历史快照）
- `MessageSource.kind` 标识生产者身份（如 `napcat:slang`、`napcat:face_summary` 等）；
- DSH 原生的 `dsh-agent-instructions` 与 `dsh-tool-skill` 均是通过挂载 `ctx.on("agent/pre-step", ...)` 钩子，各自独立判断脏检查并注入带专属 `source.kind` 的 `UserMessage`。

## 2. 目标架构设计

### 2.1 六大独立通道规划

| 通道 ID (`kind`) | 模块名称 | 体积特征 | 变动频次 | 脏检查与触发条件 |
| :--- | :--- | :--- | :--- | :--- |
| `napcat:persona` | 人格设定 (Persona) | 中 | 极低（静态配置） | 配置变更 / 首次进入会话 |
| `napcat:behavior` | 行为准则 (Behavior) | 中 | 极低（静态配置） | 配置变更 / 首次进入会话 |
| `napcat:slang` | 社群黑话知识库 (Slang) | 中~大 | 低 | 黑话内容或词条更新 |
| `napcat:face_summary` | 本地表情包库存 (Sticker) | **极大** | 中低 | 调用 `collect_face` 收录/打标表情包 |
| `napcat:session_rules` | 会话规则与约定 (Rules) | 中 | 中 | 私聊约定 / 群规则变动 |
| `napcat:user_profiles` | 用户画像与群成员 (Profiles) | 小~中 | 较高 | 活跃用户变化 / 当前发言人画像变化 |

*(注：会话规则与用户画像可拆为 2 个子通道，或作为 `napcat:memory` 的细分子投影)*

### 2.2 核心流程与装配生命周期
1. **统一安全门控 (Fail-Closed Gate)**：
   - 每个通道在渲染前必须先调用 `resolveQQSessionContext(assembleCtx)`；
   - 若不属于合法 QQ 会话（如 Web 临时沙箱、Review 沙箱），全部通道坚决静默，不注入任何消息。
2. **Per-Session 脏检查与投影状态池 (Projection State)**：
   - 维护 `retainedSnapshots = Map<sessionId, Map<channelName, string>>`；
   - 在 `agent/pre-step` 触发时，对当前有效 QQ 会话评估各个通道的新文本；
   - 若当前文本与该通道上一次 retained 文本一致，则跳过（**0 Token**）；
   - 若不一致，生成一条独立的 `UserMessage`，更新该通道的 retained 记录，并注入到 `messages` 队列中。
3. **消息格式与语义**：
   - 文本体使用统一的 PromptFormatter 排版；
   - 消息源明确声明 `source: { kind: channelName, form: 'snapshot', sections: [{ name: channelName, text }] }`；
   - 外层可保留清晰的 `<system-reminder>` 标记与局部覆盖提示，使大模型明确感知。
