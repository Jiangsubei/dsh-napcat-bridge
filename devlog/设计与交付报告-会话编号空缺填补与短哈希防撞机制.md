## 1. 需求与问题背景

### 1.1 现象与诉求
在用户或群聊会话生命周期中，若此前已依次创建了会话 1、2、3，随后用户在 Web UI 侧边栏删除了会话 1 和会话 2（仅保留会话 3）：
- **历史旧行为**：原系统在执行 `/新建`（或新进消息）时，采用纯单调递增策略（`highest.version + 1`），直接新建为「会话 4」；
- **用户期望**：新建会话应采用**空缺填补**策略，优先分配会话 1，再次新建分配会话 2；直到检测到已有活跃的会话 3，则跳过 3 继续分配会话 4；已归档的会话不参与当前活跃编号占用计算。

### 1.2 DSH 底层约束（实测事实）
在 DSH 0.2.x 体系中：
1. **展示标题（Session Title）**：完全允许重名（如 Web UI 可以同时显示多个同名 `#1`，解归档亦无冲突）；
2. **底层 SessionId**：为全局唯一主键。若会话仅在 Web UI 被归档，其 ID 仍在 DSH 内存与持久化映射中注册。若直接复用完全相同的 SessionId 调用 `sessions.create()`，会触发抛错：`Error: session "xxx" already exists`。

## 2. 方案 A 架构设计

### 2.1 规范与命名规则
采用**「语义展示编号 + 物理防撞短哈希」**设计：
- **格式**：
  - 基础轮次：`qq-group-<id>-<version>-<hash>`（例如 `qq-group-3000000001-1-a7b3c9`）；
  - 多轮归档：`qq-group-<id>-r<round>-<version>-<hash>`（例如 `qq-group-3000000001-r1-2-c4e1f8`）；
  - 短哈希：采用 6 位十六进制安全随机串（$16^6 \approx 1677$ 万种组合），防撞且长度克制。
- **向下兼容机制**：
  - 兼容旧版历史无哈希会话（`qq-group-123456`、`qq-group-123456-2`、`qq-group-123456-r1-1`）；
  - `parseSessionId` 支持可选的哈希段匹配：`^qq-group-([0-9a-zA-Z_]+?)(?:-r(\d+))?(?:-(\d+))?(?:-([0-9a-fA-F]{4,16}))?$`。

### 2.2 编号空缺填补算法 (First Missing Positive)
在 `src/gateway/session.ts` 中实现：
```typescript
export function findSmallestAvailableVersion(activeVersions: Iterable<number>): number {
  const set = new Set(activeVersions);
  let v = 1;
  while (set.has(v)) {
    v++;
  }
  return v;
}
```
- 扫描当前 peer 的未归档活跃会话版本集合（例如删除 1、2 后仅存 `{3}`）；
- 从 1 开始寻找最小未占用的正整数：
  - 第 1 次新建：分配编号 1（标题格式化为 `#1`）；
  - 第 2 次新建：分配编号 2（标题格式化为 `#2`）；
  - 第 3 次新建：活跃集合变为 `{1, 2, 3}`，跳过 3，自动分配编号 4（标题格式化为 `#4`）。

### 2.3 物理防撞与解归档和谐共存
当分配目标版本 `nextVersion` 时：
1. 优先尝试标准的 `candidateId`；
2. 若检测到该 ID 在历史中已被物理占用或处于 Web UI 归档集（`isSessionArchived` 或 `isSessionPhysicallyPresent` 为 true）：
   - 自动生成 6 位短哈希（`generateSessionHash`），组装防撞 ID；
   - 彻底避免 `session already exists` 报错；
   - 用户从归档恢复旧会话 1 时，新老会话底层 SessionId 互不相同，数据完全隔离、和谐共存。
