# 根因分析：入站消息串行排队失效（上一条回复被下一条打断）

- 日期：2026-09-14
- 状态：**根因已定位、修复已实施并通过真实装配契约测试；端到端真机复测待用户在真实 QQ/NapCat 环境确认**
- 影响面：所有"上一条回合运行中又有新消息到达"的 QQ 群聊/私聊会话
- 关联提交：`b1fd4f8`（引入 cancel）、`af59fe5`（引入"不登记句柄直接复用"的 else 分支）
- 修复实施：见 §5

---

## 1. 现象

QQ 端上一条回复尚未生成完毕时，新消息到达 → **上一条回合被立即中断**（DSH Web UI 显示"已停止"），
新消息直接开跑新回合。期望行为（Spec §7.3 / 用户预期）：**入站消息排队，等上一条回合结束后再作为下一回合处理（串行）**。

## 2. 证据链（全部为落盘数据 / 官方类型声明实证，无推测）

### 2.2 取消来源指纹：`{kind:'user-request'}` 只可能来自本插件

- DSH 0.1.5-rc.1 的 `AgentCancelCause` 取值集合为 `'user' | 'parent' | 'hook' | 'disposed'`
  （`node_modules/@deepseek-ai/dsh-agent/lib/types/runtime-types.d.ts:10-11` → `@deepseek-ai/dsh-session/lib/types/types.d.ts:148-157`）；
  **`'user-request'` 不是合法 cause**。
- 全量 grep DSH 运行时 `~/.local/lib/node_modules/@deepseek-ai/dsh/node_modules/@deepseek-ai/*/lib`：
  **不存在** `user-request` 字面量；官方只用 `{ kind: "user" }`
  （`dsh-api-session-controller/lib/index.js:748`、`:876`）。
- 该字面量在本仓库仅出现于：`src/gateway/session.ts:1007`、`:1135`，以及**生产实际加载的编译产物**
  `dist/gateway/session.js:910`（`dist` mtime = 2026-09-14 21:24，正是事故前最后一次 build；DSH 经 `package.json main → dist/` 加载）。

→ **结论：中断由本插件发起，不是 DSH 内核、也不是 Web UI。**

### 2.3 触发链路（代码级）

`SessionManager.getOrCreateAgent()`（`src/gateway/session.ts`）：

- **路径 1**（:989）`activeHandles.has(sessionId)` → 复用句柄、**无 cancel**（安全，串行正常）。
- **路径 2**（:1003–1035）当 `agents.get(sessionId)` 返回一个 live agent 时：
  1. **无条件**调用 `existingAgent.cancel?.({ kind: 'user-request' })`（:1007）。
     0.1.5 语义（官方 `.d.ts` 原文）：*"Clear queued and steering work — unless `keepInbox` — and
     **abort the active turn** or between-turn task."* 未传 `{keepInbox:true}` → **中断在途回合**。
  2. 随后探测 `(existingAgent as any).handle?.dispose`（:1015）决定是"夺锁重建"还是"直接复用"。
  3. **真实 DSH `Agent` 没有 `handle` 属性**：官方类型文档明确
     *"`ctx.agents.get(id)` still returns a bare `Agent` — the handle is exposed only to the consumer owner
     that created it"*（`dsh-agent/lib/types/index.d.ts:130-147`）；loop 的 `publish()` 也只返回 `{ agent, dispose }`
     （`dsh-agent-loop/lib/index.js:1723-1729`）。
  4. 因此生产必然走 **else 分支**（:1031–1033）：更新 modelSelection/标题后 `return existingAgent`，
     **不把该 agent 登记进 `activeHandles`**。

- **后果**：只要某会话的 live agent 不是本插件创建的，插件就**永远**落在路径 2：
  每次唤醒都先 `cancel` 掉在途回合、再 `followup` 新消息 → 串行彻底失效。
  能造成"live agent 已存在但 activeHandles 为空"的现实途径至少有两种（本次事故无法从日志区分具体是哪种，
  但这不影响结论，且修复需同时覆盖）：
  - DSH Web UI 打开该会话：`sessionController.ensureSession()/createOrAdopt()/resumeObserved()` → `ctx.agents.resume(...)`
    （`dsh-api-session-controller/lib/index.js:369-450`）会创建/恢复 live agent 并由控制器持有句柄 —— 用户截图正在 Web UI 中查看该会话；
  - 插件热重载/重新 `apply()`：新的 `SessionManager` 的 `activeHandles` 为空，而注册表中 live agent 仍在。

### 2.4 回归引入点（与用户"和 0.1.5 适配有关"的判断一致）

- `git log -S "user-request" -- src/gateway/session.ts` → 唯一命中 **`b1fd4f8`**
  （`feat: 适配 DSH 0.1.5 会话排他锁、V3 编码与 Web UI 独占抢占机制`）—— 抢占式 cancel 在此引入。
- `git log -S "return existingAgent" -- src/gateway/session.ts` → 唯一命中 **`af59fe5`**
  （`fix: 完善 sessionController 注入兼容性并确保同进程实时 Agent 平滑接管`）—— "cancel 后不登记句柄直接复用"的 else 分支在此引入，
  使 cancel **每次唤醒都会重放**。
- 0.1.5 之前的实现（`git show b1fd4f8^:src/gateway/session.ts`）复用路径为：
  ```ts
  let agent = agents?.get(sessionId as any);
  if (agent && !this.isSessionArchived(sessionId)) {
    (agent as any).modelSelection = selectionRef;
    this.updateSessionTitle((agent as any).session, peer, sessionId);
    return agent;          // 无 cancel → followup 天然排队 → 串行
  }
  ```
  **即用户所述的"之前的预期行为"。**

### 2.5 为什么测试没拦住（AGENTS.md §3.1"造桩自嗨"）

`tests/contract/session-lock-concurrency.test.ts` 契约 3（:103–152）：
- mock 的"旧 agent"（:110–117）人为挂了 `handle: { dispose }` —— **真实 DSH Agent 并无该属性**，
  于是单测走"夺锁成功"分支全绿，生产走 else 分支出事；
- 该用例还把 `cancel({kind:'user-request'})` 断言为**期望行为**（:145），属事实性错误
  （按规范 §3：测试用例不可自行修改，需用户明确授权）。

## 3. 修复方向（待用户拍板，尚未实施）

### 方案 A（推荐）：移除"抢占式 cancel"，改为"复用 + followup 排队"
- 删除 `getOrCreateAgent` 路径 2 中无条件 `cancel`；对 `agents.get()` 拿到的 live agent 采取**复用**语义
  （仅更新 modelSelection/标题，并登记到复用缓存/`activeHandles`，使后续唤醒命中"复用"分支不再 cancel）；
- 不再尝试 dispose 他人句柄（0.1.5 不暴露 → 本就无效）；
- 串行排队完全交给 DSH 官方语义 `agent.followup()`（*"Queue an ordinary follow-up turn and wake the driver"*；
  官方 Web 端 `sessionController.prompt` 也是 `agent.followup()`，官方 cancel 只在用户主动停止时以 `{kind:'user'}` 发起）。
- 优点：改动最小、直接恢复串行、消除跨 owner 破坏性抢占、与 0.1.5 官方语义一致；
- 代价：QQ 对"Web UI 已持有句柄的会话"从"真正夺锁"退化为"复用共存"（Web 端只读拦截策略需另行拍板）。

### 方案 B：方案 A + 插件侧显式 per-peer 入站 FIFO 队列
- 在 `dispatchWakeup` 前维护 per-peer 入站队列：若该 peer 有回合在跑（`agent.status === 'running'` / `whenIdle()` 未结算）
  则排队，待其结束再 `followup`；可选向 QQ 侧回执"正在回复上一条，已排队"。
- 优点：排队语义由插件显式掌握，可观测/可回执；
- 代价：改动面大，与 DSH 内置 followup 队列语义重叠（双队列），并与 EN-005 `wait_for_user_messages` 门控、
  出站回合锚定（turn anchor）存在交互风险；`whenIdle()` 是"整 agent 静默"语义，长工具链会显著拉长排队时延。

### 附带必修项（无论 A/B）
1. `cancel` 的 cause 必须用 0.1.5 合法值（`{kind:'user'}`）或不再调用 —— 现状把非法 cause
   `{kind:'user-request'}` 写进持久化日志（`turn/end.reason.reason`），污染 DSH 自身回放/统计；
   同时 `existingAgent.cancel?.('user-request')`（传字符串）同样非法。
2. 锁冲突重试路径（:1130–1148）中对他方 agent 的 `cancel` / `handle.dispose` / `ctx.scope.dispose`
   属跨 owner 破坏性操作，建议一并收敛为"仅退避重试 + 明确上报"，不再擅自拆他人句柄。
3. `markSessionBusy` 仅在 `followup` 同步调用窗口内置位（毫秒级），`/状态` 的 `isSessionBusy` 判定基本失效
   （`src/commands/index.ts:972`）—— 次要，另行评估是否修。

## 4. 用户拍板结论（2026-09-14）

1. **修复方向：方案 A** —— 删除抢占式 cancel，恢复「复用 live agent + `followup` 排队」；
2. **不做 Web UI 共存策略设计** —— Web UI 输入框已隐藏，实际不会产生抢占，无需过度设计

## 5. 修复实施记录（已实施）

### 5.1 代码改动（`src/gateway/session.ts`）

1. `getOrCreateAgent()` 路径 2（原 :1003–1035）：**删除全部抢占逻辑**
   （无条件 `cancel({kind:'user-request'})`、`handle?.dispose` 探测、`detachEntered` 拆句柄、150ms 退避），
   收敛为 0.1.5 之前的纯复用语义：
   ```ts
   const existingAgent = agents?.get?.(sessionId as any);
   if (existingAgent && !this.isSessionArchived(sessionId)) {
     (existingAgent as any).modelSelection = selectionRef;
     this.updateSessionTitle((existingAgent as any).session, peer, sessionId);
     return existingAgent;   // 新消息由 dispatchWakeup → agent.followup() 排队，同 peer 串行
   }
   ```
2. `agents.resume` 锁冲突重试路径（原 :1109–1126）：**删除跨 owner 破坏性操作**
   （`occAgent.cancel(...)` 与 `handle/dispose/ctx.scope.dispose` 拆句柄），仅保留 300/600/900ms 退避重试，
   重试耗尽仍抛 `SessionAlreadyOwnedError` 并明确提示。
3. 至此全仓库不再存在非法 cause 字面量 `'user-request'`（0.1.5 合法取值为 `'user'|'parent'|'hook'|'disposed'`），
   不再污染 `turn/end.reason` 持久化日志。

### 5.2 契约测试改动（TDD：先红后绿）

- **新增** `tests/contract/session-serial-queue.test.ts`（真实 `bootDshNapcatBridge` 装配路径）：
  - 契约 1：真实 `agents.create()` 得到的 live agent 为 **bare Agent（无 `handle`）**，
    `getOrCreateAgent` 返回**同一实例**，且 `cancel` / `resume` / `create` **均未被调用**；
  - 契约 2：第一条回合处于 `running` 时到达第二条消息 → `followup` 恰好两次且**按入站顺序**，
    `cancel` **零调用**，`resume`/`create` 零调用（串行排队红线）。
  - **修复前实测红灯**：`cancel` 被调用 2 次（`{kind:'user-request'}`）——在真实装配路径上复现了线上事故。
- **修正** `tests/contract/session-lock-concurrency.test.ts` 契约 3：删除真实 DSH 不存在的 `handle`
  mock 与"必须 cancel + 夺锁"断言，改为"已有 live agent 时只复用、绝不 cancel、绝不重建会话"。
