# 方案设计：统一附件描述符（Attachment Descriptor）

> 日期：2026-11-05　状态：已实施（单测/契约已全绿，待真机验证）
> 范围：入站/出站的图片、表情包、文件（首期）；语音/视频/合并转发/卡片做描述与渲染，不做新增落盘。
> 原则：不分别打补丁，抽统一附件模块；入站出站共用一套描述符；所有消息附件通用，不止表情。

---

## 1. 背景与目标

### 1.1 两处现象

**现象 A：自发表情落库到历史只剩 `file:///` 路径，没有 face_id / 情绪标签**

链路：

1. `src/tools/index.ts` 的 `sendFace()` 构造段时只给 `file`（`file:///` URI）与 `sub_type`，没有 `local_path` / `md5` / `face`。
2. `src/gateway/server.ts` 的 `notifyOutboundSent()` 把原始 payload 原样交给 `onMessageSent`。
3. `src/outbound/self-record.ts` 的 `buildSelfMessageRecord()` 复用 `parseNormalizedContent()`。
4. `src/gateway/wakeup.ts` 的 image 分支在无 `data.face` 时尝试 `getFaceByMd5`，但 MD5 推导只认 `data.md5`、`data.local_path`、或纯 MD5 文件名；`file:///` URI 三者都不满足，匹配不到表情库。
5. 又因 `data.sub_type === 1`，最终渲染成 `[表情包:${data.file}]`，即 `[表情包:file:///...]`。

结论：`getFaceByMd5` 已注入，缺的是**附件事实**（本地路径 / MD5 / face 元信息）。

**现象 B：本地落 jpg，但 `file_id` 写 `.png`**

两个可能来源（同一设计缺陷）：

- 入站：`messages.file_id` 取 `data.file || data.file_id`（QQ/NapCat 远端伪名，自带后缀）；`saveBuffer` 落盘以字节魔数决定扩展名。二者语义未分层。
- 出站：`enrichOutboundMediaRecord()` 用 `get_msg` 返回段的 `data.file` 覆盖 `file_id`；NapCat 回查的缓存名后缀可能与本地源文件不同。

共同根因：**远端标识（file_id）与本地事实（local_path / format）没有分离**。

### 1.2 现状的重复推断点

| 语义 | 位置 |
|---|---|
| 是否表情包（sticker） | `src/index.ts`、`src/gateway/sync.ts`、`src/gateway/wakeup.ts`、`src/outbound/self-record.ts` 各一份 |
| `file_id` 来源 | 上述入站/同步/出站各一份 |
| 本地路径/格式/表情匹配 | `src/gateway/inbound-media.ts` + `src/storage/media.ts` + `src/index.ts` |
| 文本渲染 | `src/gateway/wakeup.ts` 的 `parseNormalizedContent()` 大 switch，被入站、出站、引用、历史重解析共用 |
| 出站元数据 | `src/outbound/self-record.ts` 的 payload 反推 + `get_msg` 回查 |

### 1.3 目标

1. 建立唯一附件事实源 `AttachmentDescriptor`，入站/出站共用。
2. 统一 kind 判定、统一渲染、统一落库字段映射。
3. `file_id`（远端）与 `local.format`（本地，以魔数为准）彻底解耦。
4. 出站文案改进：不再展示 `file:///` URI；表情命中库时展示 face_id + 情绪。
5. 接通 `payload.images` → DSH `ImageBlock`，让模型真正收到图片。
6. 首期不新增语音/视频落盘，不改变 P5 能力边界。

## 2. 设计

### 2.1 模块结构

新增 `src/attachment/`：

```
src/attachment/
  types.ts      描述符与辅助类型
  classify.ts   唯一的 kind 判定 + 段内事实提取 + 主导类型/媒体字段映射
  render.ts     唯一文本渲染（入站/出站/引用/历史重放共用）
  outbound.ts   出站描述符构造 + 消息段归一化
  store.ts      描述符 ↔ MessageRecord/DB/raw 的序列化、反序列化与回退
```

> 实施说明：未单独创建 `ingest.ts`。入站 IO（`resolveInboundImage` /
> `downloadPrivateFile`）继续留在 `src/index.ts` 的既有流程中，等落盘与表情库匹配完成后
> 再统一调用 `describeMessage()` 提取事实，避免为纯函数层引入 IO 依赖。

核心约束：

- 纯函数优先；IO（落盘、gateway、DB）由调用方注入。
- 不在描述符里存 `undefined` 字段；可选字段用条件展开。
- 不修改 `resolveInboundImage` / `downloadPrivateFile` 的取图策略。

### 2.2 描述符模型

```ts
export type AttachmentKind =
  | 'image' | 'sticker' | 'file' | 'group_file'
  | 'record' | 'video' | 'forward';

export type AttachmentOrigin = 'inbound' | 'outbound';

export interface AttachmentRemoteMeta {
  /** QQ/NapCat 侧标识；原样保留，不参与本地后缀推断 */
  fileId?: string;
  busid?: number;
  url?: string;
  forwardId?: string;
}

export interface AttachmentLocalMeta {
  path: string;
  /** 真实格式，以字节魔数为准（png / jpg / gif / webp / dat ...） */
  format?: string;
  size?: number;
  md5?: string;
  /** SHA-256 本地去重指纹 */
  fingerprint?: string;
}

export interface AttachmentFaceMeta {
  id: string;
  mood?: string;
  tags?: string[];
}

export interface AttachmentDescriptor {
  kind: AttachmentKind;
  origin: AttachmentOrigin;
  remote?: AttachmentRemoteMeta;
  local?: AttachmentLocalMeta;
  face?: AttachmentFaceMeta;
  summary?: string;
  fileName?: string;
  /** 未落盘/发送失败原因；用于渲染，不参与猜路径 */
  unavailable?: string;
}
```

### 2.3 kind 判定（唯一规则）

`classify.ts` 提供：

```ts
export function classifySegment(seg, ctx: { isGroup }): AttachmentKind | null;
export function describeSegment(seg, ctx: { origin, isGroup }): AttachmentDescriptor | null;
export function describeMessage(segments, ctx): { type: string; attachments: AttachmentDescriptor[] };
export function inferDominantType(segments, ctx): string;
export function toMessageMediaFields(description): MessageMediaFields;
export function isStickerSegment(data): boolean;
```

首期规则（与现有落库口径对齐）：

- `seg.type === 'image'`：
  - `data.sub_type === 1 || data.emoji_package_id` → `sticker`
  - 否则 → `image`
- `seg.type === 'file'`：
  - `isGroup` → `group_file`
  - 否则 → `file`
- `record` / `video` / `forward` → 同名 kind
- 其他（text/at/reply/json/xml/mface/...）→ `null`（`mface/marketface` 首期保持既有行为，不单独判定）

远端标识规则：

- `remote.fileId` 优先取 `data.file_id`；
- 仅 `image` / `record` / `video` 允许在无 `file_id` 时用 `data.file` 作为远端标识；
- `file` / `group_file` 的 `data.file` 通常是文件名（如 `report.pdf`），**绝不**当作远端 ID。

主导类型规则（`inferDominantType`）：`file / forward / record / video / poke / shake / json / xml`
无条件覆盖；`image / reply / at` 仅在类型仍为 `text` 时生效。

> 注：`emoji_id` 目前只在“是否表情/主动回复排除”逻辑中使用，不改变落库 type；首期保持该行为，避免无谓行为漂移。

### 2.4 入站数据流

```
onMessage(event)
  ├─ image/sticker → resolveInboundImage()（保留四段式主路）
  ├─ 私聊 file    → downloadPrivateFile()（保留两级退化）
  ├─ 落盘后：MD5 匹配本地表情库 → 回写 data.md5 / data.fingerprint / data.face
  → describeMessage(event.message, { origin:'inbound', isGroup })
  → parseNormalizedContent(event) → renderAttachment()（唯一渲染入口）
  → saveMessage({ ...toMessageMediaFields(description), attachments })
```

要点：

- `index.ts` 删除重复的 `dominantType/fileId/busid/primaryLocalPath` 推导，统一从 descriptors 取。
- `gateway/sync.ts` 离线同步不再各写一套判定；使用同一 `describeMessage()` + `toMessageMediaFields()`，媒体仍不落盘（保持现状）。
- 群文件保持懒加载语义，只做描述与落库字段。
- `parseNormalizedContent` 在图片分支会做一次 MD5 表情库匹配（覆盖入站、出站自记录、引用重解析、历史重放），
  普通 `image` 段命中表情库时与 `sticker` 一致渲染为语义占位符。

### 2.5 出站数据流

```
sendFile / sendFace
  → buildOutboundAttachments(...) 生成 descriptors（含 kind/local/face/remote）
  → sendMsg(peer, payload, descriptors)
  → gateway.notifyOutboundSent(..., descriptors)
  → OutboundSentEvent.attachments
  → buildSelfMessageRecord() 直接消费 descriptors
  → enrichOutboundMediaRecord() 只补 remote（file_id/url/busid），绝不改 local/face/kind
```

传递方式：**方法参数旁路**，不塞进发给 NapCat 的段，避免依赖“NapCat 忽略未知字段”这个未证实假设。

接口调整：

- `sendAction(action, params, timeoutMs?, attachments?)`
- `sendGroupMsg(groupId, message, attachments?)`
- `sendPrivateMsg(userId, message, attachments?)`
- `sendMsg(peer, message, attachments?)`
- `OutboundSentEvent.attachments?: AttachmentDescriptor[]`

### 2.6 文本渲染规范（改进后）

`render.ts` 是唯一入口。`file:///` URI 一律先转 OS 路径；远程 URL 不伪装成本地路径。

| 场景 | 输出 |
|---|---|
| 命中表情库（入站/出站，含普通 image 段 MD5 命中） | `[表情包: <face_id> (情绪: <mood>)]`；无 mood → `[表情包: <face_id>]` |
| 表情包未命中库、本地有路径 | `[表情包:<summary 或 "表情"> 已保存: <path>]` |
| 表情包未命中库、无本地路径 | `[表情包:<summary>]`；无 summary → `[表情包]` |
| 普通图片、本地有路径 | `[图片:<path>]` |
| 普通图片、仅远程 URL | `[图片:<url>]` |
| 普通图片、既无本地也无 URL | `[图片]` |
| 群文件 | `[群文件:<name>]`；有 file_id → `[群文件:<name> (ID:<file_id>)]` |
| 私聊文件、本地有路径 | `[文件:<name> 已保存: <path>]` |
| 私聊文件、入站落盘失败 | `[文件:<name> (入站落盘失败)]` |
| 私聊文件、无本地路径且无失败标记 | `[文件:<name>]` |
| 语音 / 视频 / 合并转发 | 保持 `[语音]` / `[视频]` / `[合并转发 (ID:...)]` |

> 文案风格：除命中表情库的 `[表情包: face_x (情绪: y)]` 外，其余保持既有的无空格风格，
> 与存量历史文案兼容。

关键变化：

- 出站 `send_face` 命中库 → 与入站完全一致，不再出现 `file:///`。
- 出站 `send_file` 图片 → `[图片: /abs/path]`，文件 → `[文件: name 已保存: /abs/path]`。
- 未落盘不再猜 `data.file`（可能是伪名/URI）。

### 2.7 存储

`messages` 表新增：

```sql
ALTER TABLE messages ADD COLUMN attachments TEXT;
```

- 存精简描述符 JSON 数组（不含 `segment`，raw 已有原始段）。
- `MessageRecord.attachments?: string | null`；`ChatMessageSummary.attachments?: string | null`。
- `saveMessage` / `saveMessageIfNotExists` 写入；`getMessage` / `readHistory` 读出。
- **存量回填（用户拍板：能回填就回填，不能回填保持 NULL）**：
  - 在 `MessageDatabase.init()` 中执行一次性迁移 `backfillAttachmentsOnce()`；
  - 只扫描 `attachments IS NULL` 的历史记录，绝不覆盖已有值；
  - 第一优先级：解析 `raw` 消息段 → `describeSegments()`（信息最全，含 face / local / remote）；
  - 第二优先级：`raw` 不可解析时，用结构化列 `type / file_id / busid / local_path / content` 保守合成；
  - 两者都确认不到任何附件事实时，保持 `NULL`，绝不编造空描述符；
  - 完成后写入 `plugin_kv` 标记 `messages_attachments_backfill_v1`，后续启动不再扫描全表；
  - 回填失败不阻断启动（不写标记，下次重试）；
  - **只回填 `attachments` 列，不改写 `content` / `raw`**，避免历史文案被静默重写。

### 2.8 payload.images 接通（DSH 真实契约）

已核对 `@deepseek-ai/dsh-llm` 与 `@deepseek-ai/dsh-attachment`：

- `UserMessage.content` 是 `ContentBlock[]`；
- 图片块为 `{ type: 'image', attachment: ImageAttachmentRef }`；
- `ImageAttachmentRef` 必须由 `ctx.attachments.saveImage({ data, mediaType, name })` 生成，不能伪造路径或 base64 URL；
- DSH 会自行把图片投影给支持图片的模型，text-only 模型自动降级为占位文本。

实现：

- `agent-runner.dispatchWakeup()` 构造 user message 时，若 `payload.images` 非空：
  - 过滤出真实存在、且魔数可识别为 png/jpeg/webp/gif 的本地文件；
  - 逐张 `ctx.attachments.saveImage(...)`；
  - 追加 `{ type:'image', attachment }`；
  - 单张失败只 `warn`，不阻断文本消息；
  - attachments 服务不可用时降级为纯文本。
- 保持 `formatWakeupPrompt` 文本不变（内容中已有附件占位）。

### 2.9 兼容与边界

- **不改** `resolveInboundImage` 的四段式取图顺序。
- **不改** `downloadPrivateFile` 的两级退化。
- **不改** 表情库 `faces` 表结构。
- **不改** 语音/视频/合并转发的现有展示与落盘行为。
- 出站 `get_msg` 回查仍保留，但只补 remote；payload 版本优先。
- 所有 `defineTool` 返回继续经过 `toLosslessJson`，本次不新增工具。

## 5. 风险与对策

| 风险 | 对策 |
|---|---|
| 出站描述符在串行队列闭包中丢失 | descriptors 与 payload 一起闭包捕获，显式传入 `sendMsg` |
| `get_msg` 回查覆盖本地事实 | 只允许补 remote；测试断言 local/face 不被覆盖 |
| `file_id` 后缀污染本地路径 | 描述符分 `remote.fileId` / `local.format`；渲染只用 local |
| 图片接通导致 text-only 模型报错 | 依赖 DSH 投影；失败单张降级；attachment 服务缺失降级纯文本 |
| 旧数据无 `attachments` | 一次性迁移回填：raw 优先、结构化列兜底、无法确认保持 NULL；只回填列不改 content |
| 契约文案变更面过大 | 统一渲染严格按 §2.6 表；只改因文案变化失败的断言，不放宽 |

## 6. 非目标（首期明确不做）

- 存量消息 `content` 的重渲染（只回填 `attachments` 列，历史文案保持原样）。
- 语音、视频、合并转发的新增落盘与转码。
- `mface/marketface` 的取图兜底（只描述与渲染）。
- 表情库 `faces` 表结构变更。
- `payload.images` 的卡片封面/远程 URL 下载（只接本地已落盘图片）。
