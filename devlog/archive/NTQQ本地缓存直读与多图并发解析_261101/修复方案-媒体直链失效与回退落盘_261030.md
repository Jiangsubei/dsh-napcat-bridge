## 0. 结论速览

| 问题 | 判定 |
|---|---|
| 直连 `gchat.qpic.cn` 报 400 `-5503007 download url has expired` | **不是"图太旧过期"，也不是并发/网络抖动**：P0 日志里**真实下载 19 次全部瞬时失败**，都在收到消息后 100~160ms 内，retmsg 名不副实 |
| 究竟是什么 | 消息段里那条 `gchat.qpic.cn/download?...&rkey=...` 的 **rkey 对我们这个账号/进程不成立**，QQ 侧统一回 "expired"。同账号走 NapCat/QQ 客户端自己的取图链路（自己的 rkey）100% 成功 |
| 回退成功了却不落盘、不拼路径 | **代码事实**：`MediaProbe.probeFallback()` 在 P0 就是**纯观测**（不落盘、不改库、fire-and-forget），`src/index.ts` 的 catch 里只记日志，`data.local_path` 从未被回填 → `parseNormalizedContent` 退化成 `[图片:<data.file>]` |
| 要不要先起探针 | **不必单独起探针**：本机已有硬证据（见 §1）；剩下唯一未知（`get_msg` 刷新的 rkey 能不能用）可以直接做进修复的第 4 顺位分支，由生产日志自答，不用额外实验 |

## 1. 证据（本机实测，非推断）

### 1.1 P0 观测日志（`<DSH_HOME>/napcat/logs/media-20261030.log`）

`node scripts/media-log-report.mjs` 输出：

~~~text
入站 image 段: 42 | 落盘成功: 23（去重命中 22）| 落盘失败: 19
真实下载成功率: 5.0%（真实下载 20 次）
失败响应体: 19/19 = {"retcode":-5503007,"retmsg":"download url has expired"}
失败 host:  19/19 = gchat.qpic.cn
兜底可用率: get_image 19/19 | get_file 19/19 | get_msg 19/19（全部 100%，has_path + path_exists 均 true）
~~~

关键点：**23 次"成功"里 22 次是一级去重命中（`dedup_level:1`，根本没下载）**，唯一一次真实下载成功是 `gxh.vip.qq.com`（个人表情包，无 rkey）。
即：今天 `gchat.qpic.cn` 的真实下载 **0 成功 / 19 失败**，不是 44% 概率问题，是 100% 失效。

同时失败发生在**收到消息后 100~160ms**（例：`image_seen` 09:21:59.992 → `image_failed` 09:22:00.143，消息发送时间 09:22:00）。
所以"链接过期"这个 retmsg 至少不可能是"放久了失效"。

### 1.2 生产库 raw 段：host 在 10-28 15:50 前后发生切换

按 raw 里 image 段的 `url` 统计（只统计 host / appid / 是否带 rkey，不落 query）：

~~~text
multimedia.nt.qq.com.cn/download?rkey  appid=1407   saved=1465  null=1271  (08-30 → 10-28 15:19)
multimedia.nt.qq.com.cn/download?rkey  appid=1406   saved=  80  null=   9  (08-30 → 10-28 15:47)
gchat.qpic.cn/download?rkey            appid=1407   saved=  29  null=  86  (08-30 → 10-30 02:21)
gchat.qpic.cn/download?rkey            appid=1406   saved=  18  null=   4  (10-28 15:58 → 10-30 02:27)
gchat.qpic.cn/gchatpic_new（无 rkey，公开直链）      saved=  28  null=  17  (08-31 → 10-29 15:51)
~~~

两个结论：

1. **10-28 15:50 之前**，入站图片 URL 基本都是 `multimedia.nt.qq.com.cn/download?rkey=...`，真实下载能成；
2. **10-28 15:50 之后**，URL 基本换成 `gchat.qpic.cn/download?rkey=...`，此后 `saved` 全是去重命中（对照 §1.1 的 `dedup_level:1`），**凡是需要真实下载的都 NULL**；
3. 老式 `gchatpic_new` 公开直链（不带 rkey）一直还能下（最近一条 10-29 15:51 成功）——说明"我们进程的出口网络/UA/Referer 没问题"，坏的是**带 rkey 的那个 download 端点**。

### 1.3 直连实验：改 header / 改参数都救不回来

拿库里一条真实失败 URL 现场试（一次性，未落盘、未写入任何项目文件）：

~~~text
plain fetch                 -> 400 -5503007 download url has expired
UA=QQ/9.9.15                -> 400 -5503007（同上）
UA + Referer=qun.qq.com     -> 400 -5503007（同上）
Referer only                -> 400 -5503007（同上）
http:// 代替 https          -> 400 -5503007（同上）
去掉 spec / 加 term+is_origin -> 400 -5503007（同上）
spec=1                      -> 400 -5503037 invalid spec or format  ← 换了报错
~~~

`spec=1` 换报错这条很重要：说明服务端**正常解析了 appid/fileid/rkey**，不是格式/转义/签名串被破坏，而是明确判定"这组凭据无效"。UA / Referer / 协议 / 附加参数都不是变量 → 不是反爬、不是 header 缺失。

### 1.4 NapCat 本地确实有原图，且是原图不是缩略图

拿失败样例 `file=972D03EA….png`（`file_size=24408`）在本机按 QQ 的 MD5 命名去找：

~~~text
<QQ_DATA>/1000000001/nt_qq/nt_data/Pic/2026-10/../Ori/972d03ea….png   24408 字节
<QQ_DATA>/1000000002/nt_qq/nt_data/Pic/2026-10/../Ori/972d03ea….png   24408 字节
<QQ_DATA>/1000000002/nt_qq/nt_data/Pic/2026-10/../Thumb/972d03ea…_*.png 59348 字节
~~~

`Ori`（原图）字节数与消息段声明 `file_size` **完全一致** → `get_image` 那条 `path_exists:true` 的路径指向的是原图，复制过来不会掉画质。
（同一个 md5 两边都有，说明 QQ 客户端各自用自己的凭据把图落到了本地缓存。）

### 1.5 代码事实：回退结果确实被丢掉

- `src/gateway/media-probe.ts:207-213` 注释与实现都写明"**纯观测（不落盘、不改库）**"，且调用侧是 `void mediaProbe.probeFallback(...)`（`src/index.ts:576/579/615`）—— fire-and-forget，返回值没人接；
- `src/index.ts:594-616`：`mediaManager.downloadAndSave` 抛错后只 `mediaProbe.failed(...)` + 探测兜底，**从不写 `data.local_path`**；
- `src/gateway/wakeup.ts:397-410`：`imgPath = data.local_path || data.file || data.url`，`local_path` 缺失就退化成裸文件名 →
  用户看到的 `[图片:972D03EA….png]` 与库里 `content` 一字不差（已比对 `msg 700000001`）。

## 2. 根因判定

**链路三段，坏在第一段，第二段被白白丢掉，第三段跟着退化：**

1. **取图凭据段（坏）**：QQ 下发的消息元素里带的是**发送侧生成的 rkey**（`gchat.qpic.cn/download`）。这个 rkey 对"我们进程/这个账号的第三方请求"不成立，QQ 统一回 `-5503007 expired`。
   证据：收到后 100ms 就失败（排除时效）、改 header/参数全无效（排除反爬/编码）、换 host 到公开直链就能下（排除网络）、QQ 客户端自己能拿到原图（说明图还在、只是凭据不对）。
   → 结论：**"过期"是 QQ 的笼统拒词，实际是"这组 rkey 不适用于我们"**。重试同一条 URL 永远没用。
2. **兜底段（有效但被丢弃）**：NapCat `get_image` / `get_file` 走 QQ 客户端自己的取图链路，19/19 成功、路径真实存在、字节是原图。
   但 P0 阶段它被明确定义为"只观测"，结果既没搬进我们的 `downloads/`，也没回填 `data.local_path`。
3. **渲染段（被动受害）**：`parseNormalizedContent` 只能拿 `data.file`（QQ 的 MD5 假名）拼 `[图片:<文件名>]`，模型看不到图、也拿不到路径。

**关于"还需要不需要探针"**：
不需要为"URL 是不是真过期"再单独起探针了——§1.3 已经把 header/协议/参数/时效全部排除，§1.1 已经给出 19/19 的确定性失败率。
唯一还没被回答的是"`get_msg` 重新取的 rkey 对这条图能不能下"（理论上也可能同样不成立）。这一条**不需要单独实验**：把它做成修复里的第 4 顺位分支，成功/失败都写一行日志（`via=get_msg_url` / `refresh_url_failed`），跑一天就能得到答案。

## 3. 修复方案

### 3.1 主路重排（同一条链路，把兜底变成主路）

新增一个入站图片解析函数（建议 `src/gateway/inbound-media.ts`，纯函数式、可注入 gateway/mediaManager，便于契约测试），
把现在 `src/index.ts:580-619` 那段"直连→失败就记日志"改成**按顺序、串行、首个成功即返回**的四段式：

| 顺位 | 手段 | 命中条件 | 说明 |
|---|---|---|---|
| 1 | `get_image({file: data.file})` → 本地路径 | `status==='ok'` 且 `data.file` 存在 | 今天 19/19 命中；本地读盘，不碰 CDN，无 400 噪音 |
| 2 | `get_file({file_id: data.file_id \|\| data.file})` → 本地路径 | 同上 | 与 1 同源，保留作兼容（不同 NapCat 版本行为不一） |
| 3 | HTTP 直连 `data.url` | 2xx | 保留：`multimedia.nt.qq.com.cn` / `gchatpic_new` 这类今天仍可用的 host 靠它兜住 NapCat 抽风 |
| 4 | `get_msg({message_id})` → 取新 url → HTTP 直连 | 2xx | 兼做"刷新 rkey 是否有效"的生产实验，结果入日志 |

要点：
- **全部 `await` 完再往下走**，不再 fire-and-forget；`downloads` 与 DB 落盘必须在构建 content 之前完成（现状本来就是先落盘后拼 content，顺序不变）。
- 每段都复用 `mediaManager.saveBuffer` / `downloadAndSave` 落盘：**落到我们自己的 `downloads/<type>/<peer>/`**，`fileId` 照旧传给一级去重，指纹照旧二级去重，扩展名照旧按魔数纠正。
- 四条全崩时保持现状（`local_path` 空、content 退化为文件名），但日志要能一眼看出是"四条都试过了"而不是"没试"。
- 现 P0 的 20 次/分钟限流只用于"观测探测"，新主路**不适用限流**（它是在解析当前消息，被限流等于丢图）。

### 3.2 落盘策略：复制进 `downloads/`，不直接引用 NapCat 缓存路径

推荐**复制**（与既有 PF-001 私聊文件的两级退化完全一致：`src/tools/private-file.ts:146` 就是 `get_file` 拿到本地路径后 `mediaManager.downloadAndSave(wslPath, …)`）。

理由（按重要性）：

1. **路径生命周期不在我们手里**：`get_image` 给的是 QQ 自己的缓存目录（`.../nt_qq/nt_data/Pic/...`）。用户在 QQ 里"清理缓存"、QQ 升级迁移、换版本目录，`local_path` 立刻变成死链接；我们的 7 天 TTL 清理也管不到它。
2. **去重/自愈体系会半瘫**：`saveBuffer` 的 SHA-256 二级去重、魔数后缀纠正、`bytes` 观测、`purgeExpiredFaces`/`clearLocalPath` 全部建立在"文件在我们目录下"这个前提上。
3. **QQ 缓存不是原图保证**：`Thumb/` 目录就在旁边，一旦某版本 `get_image` 返回缩略图，直接引用会把低清图当原图存进历史且无感知；走复制+尺寸校验才拦得住（见 3.4）。
4. 成本可接受：图片多为几十 KB~2MB，一次本地 read+write（≈1ms 级），换来的是"我们自己完全拥有这份文件"。

不推荐直接引用：省的那点 I/O 换来的是一堆"路径忽然没了但 DB 说有"的脏数据，以及清缓存后历史不可读。

### 3.3 观测增强（承接 P0，不新增概念）

新增/调整事件（沿用 `media-logs` 的 JSONL + 脱敏规则，url 只记 host）：

| 事件 | 级别 | 字段 | 用途 |
|---|---|---|---|
| `media_resolved` | info | `via`(get_image/get_file/url/get_msg_url)、`duration_ms`、`bytes`、`size_declared`、`size_actual`、`fallback_index` | 每种手段的真实占比（判断能不能把 3/4 顺位删掉） |
| `image_failed` | warn | 现有字段 + `attempts`（四条各自的结果摘要） | 全崩时能直接看出卡在哪 |
| `refresh_url_result` | info/warn | `ok`、`http_status`、`body_head` | 回答 §2 的残余未知 |
| `probe_fallback` 相关 | — | 保留；主路成功时不再触发 | 避免"已落盘还去探测"的重复调用 |

### 3.4 顺手要补的两个小坑（都在同一条路径上，不做会复发）

1. **路径形态判定太窄**：`src/storage/media.ts:255` 只认 `/` 开头或 `^[a-zA-Z]:\\`；NapCat 若回 `C:/...`（正斜杠）或 `file:///C:/...`（`replace(/^file:\/\//)` 后 URI 未解码）会被当成"不支持的 URL"。改成 `path.isAbsolute()` + `fileURLToPath()` 判定。
2. **原图/缩略图校验**：把消息段 `file_size` 与本地字节数比对，不一致就记 `size_mismatch`；不一致时**优先再试第 3/4 顺位拿原图**，本地副本作为保底（v1 也可以只记日志不改选路，二选一，见 §5-D）。

### 3.5 明确不在本次范围

- 离线同步（`sync.ts`）补落盘、mface/商城表情、引用回填脏数据（G4/G1/G6）——仍是独立任务，别混进来扩大回归面。
- 历史 1039 条 `local_path` 为空的老消息——不动（URL 已死，只能靠 get_msg 批量回捞，属于另一件事）。
- `content` 文案格式（`[图片:…]` / `[表情包:… 已保存: …]`）**一个字不改**，避免碰 wakeup 一堆契约测试。

### 7.3 段内 `local_path` 分支（实施中新增）

NapCat 若已在消息段里给出 `data.local_path`，说明它已把文件解析到本机：

- 路径可读 → 直接复制进 `downloads/`（`via: 'segment_local_path'`），**不再调用 get_image**；
- 路径不可读（QQ 清缓存 / 跨机器路径）→ 快速失败，**也不再调用 NapCat**，避免整条入站消息链路卡在一次 15s Action 超时上；调用方保持 content 原样。

该分支由既有 `quote-assembly.test.ts`（前置图片段自带 local_path）暴露：原实现会因测试客户端不应答 `get_image` 而阻塞后续消息处理。
