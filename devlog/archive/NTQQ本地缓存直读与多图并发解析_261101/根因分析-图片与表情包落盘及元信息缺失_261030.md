# 根因分析 — 图片/表情包入站落盘与模型元信息缺失（261030）

> 范围：三项同源缺陷（表情资源按消息后缀命名导致后缀失真 / 纯表情消息元信息未进模型输入 / 消息收到时未做到无条件落盘）。
> 本文只做根因定位与修复方案，**未改动任何 src/ 代码**，待拍板后按 TDD 分阶段实施。
> 证据来源：本地生产库 <DSH_HOME>/napcat/messages.sqlite（只读统计，未写入）、下载目录实盘扫描、src/ 与 dist/ 实现比对。文中所有 QQ 号/群号/用户名已脱敏。

## 0. 结论速览

| # | 现象 | 根因（已坐实程度） |
|---|------|------------------|
| 1 | 拉取表情资源存成 .gif 实际是 JPEG，读取报格式不符 | **已坐实**：saveBuffer 的「魔数纠正文件名后缀」分支被 type 门控，type:'files' 且带 filename 的下载路径（fetch_chat_resource / 入站私聊文件）完全跳过纠正，外部/模型给的后缀直接落盘 |
| 2 | 纯表情消息模型输入只剩 [表情包:[动画表情]]，无描述无路径 | **已坐实**：模型输入唯一通道是 formatWakeupPrompt 生成的纯文本；payload.images 组装后**无人消费**；无 local_path 时 content 退化为无路径、**无 file_id**；且手动补拉后 updateLocalPathByFileId 不回写 content |
| 3 | 消息收到时未做到"无条件落盘"，模型得自己下载 | **部分坐实 / 部分待观测**：落盘确实在 onMessage 入口、**先于**唤醒门控（"只落盘当前唤醒消息"的猜测不成立）；实际缺口是 mface 段未处理、url 缺失即静默跳过、失败只打 debug、离线同步不落盘、群聊下 fetch_chat_resource 把非群文件错误路由到群文件分支。**另有 44% 实时下载失败的真实错误被 debug 吞掉，必须先补可观测性才能定死** |

## 1. 证据（实测，非推断）

### 1.1 库内表情包消息落盘率

~~~text
messages 表中 type='sticker'：2142 条
  ├─ local_path 非空：1103 条
  └─ local_path 为 NULL：1039 条（48.5%），content 全部为 "[表情包:[动画表情]]"
~~~

media 事件（image + sticker）按「同 data.file 首次出现」去重后，需要**真实网络下载**的共 1481 条：成功 829 条（56.0%），失败 652 条（44.0%）。

失败与并发强相关：

~~~text
3 秒窗口内无其它待下载媒体：1371 条，成功 783（57%）
3 秒窗口内 2+ 条并发：        26 条，成功   5（19%）
~~~

近期按小时切片可见「同一小时内成功与失败交错」，**排除**"整段时间插件没运行 / 全是离线补拉"的解释。

### 1.2 后缀失真实锤（问题 1）

对 <DSH_HOME>/napcat/downloads 与 faces 全量 901 个文件逐字节嗅探魔数：

~~~text
gif->gif 172 | jpg->jpg 572 | png->png 155 | gif->jpg 1 | html->unknown 1
不匹配样本：<DSH_HOME>/napcat/downloads/files/<peer>/sticker_0100.gif   实际 = JPEG
~~~

该文件位于 files/（即 fetch_chat_resource 落盘目录），文件名用 .gif、字节是 JPEG —— 与用户描述完全一致。

### 1.3 元信息缺失 / 手动补拉实锤（问题 2）

同一条消息出现「content 无路径、local_path 却存在」的组合：

~~~text
07:10:25 sticker  local_path=OK   content="[表情包:[动画表情]]"
msg 700000002      local_path=<DSH_HOME>/napcat/downloads/files/<peer>/sticker_0710.jpg
                   content="[表情包:[动画表情]]"
~~~

说明模型确实**自己调了 fetch_chat_resource** 把文件拉到 files/，而 updateLocalPathByFileId 只 UPDATE local_path、不重写 content，所以历史记录里仍然是没路径的那句话。

### 1.4 直链时效性实锤（问题 3 的放大因素）

对库里 10 条历史 url 逐个现拉：

~~~text
HTTP 400  {"retcode":-5503007,"retmsg":"download url has expired"}
~~~

即：**收消息当下没落盘，之后这条 url 基本永久失效**，只能靠 NapCat 重新取（get_image / get_file）才能补救。当前代码既无重试、也无兜底、还不告警。

## 2. 逐项根因

### 2.1 问题 1：后缀由「调用方给的名字」决定，而不是字节

src/storage/media.ts:168-188（分支互斥）：

~~~ts
const ext = (detectedExt || options.ext || ...)   // 只在"自动命名"分支生效
let fileName = options.filename ? basename(...) : undefined;
if (!fileName) { fileName = 指纹 + '.' + ext }                      // ← 魔数在这里生效
else if ((type === 'image' || type === 'sticker') && detectedExt) {  // ← 只有 image/sticker 才纠偏
  // 用魔数改后缀
}
~~~

两个问题：
1. 纠偏分支只对 image / sticker 生效；
2. fetch_chat_resource 走 downloadPrivateFile，固定 type:'files'（src/tools/private-file.ts:95-100），且把消息里的 file_name / data.file 原样当 filename（src/index.ts:593、src/tools/index.ts:198/219）。→ JPEG 字节 + .gif 名字，直接落盘。

连锁污染（同一根因的下游）：
- collectFace 用**本地路径后缀**当表情库 format（src/tools/index.ts:998、1024）→ 表情库 format 错误；
- face-routes 预览按后缀给 Content-Type（src/server/face-routes.ts:252-254）→ 图片打不开；
- read_image 按后缀解码 → 报"格式不符"，用户被迫手动改后缀。

### 2.2 问题 2：唯一进模型的通道是纯文本，images 是死数据

- 模型输入构造：src/gateway/session/agent-runner.ts:520-525 → createUserMessage 只装一个 text 段（formatWakeupPrompt 的返回值），**只取文本**。
- shouldWakeup 里组装的 payload.images（src/gateway/wakeup.ts:745-813）**在整个仓库没有任何消费方**（grep payload.images 仅命中赋值处）。
- 于是模型看到的"图片/表情信息"完全取决于 parseNormalizedContent 拼出来的那行字（src/gateway/wakeup.ts:397-410）：

~~~text
有 local_path → [表情包:<summary> 已保存: <path>]
无 local_path → [表情包:<summary>]        ← 无路径、无 file_id、无格式、无尺寸
~~~

- summary 本身只有 [动画表情] 这种占位，没有画面描述（NapCat 也只给这一字段）。
- 补拉后不回写 content（1.3 实锤）→ 下次读历史依然是空信息，形成"反复拉取"。

### 2.3 问题 3："无条件落盘"没做到，且失败不可见

**先否掉一个猜测**：落盘代码在 onMessage 最前段（src/index.ts:538-578），早于 shouldWakeup（:787）与等待门控（:732），对每个入站事件都会执行 —— 不存在"只落盘当前唤醒消息"的分支。证据：大量**未唤醒**的群消息同样有 local_path。

真正的缺口（按影响排序）：

| 编号 | 缺口 | 位置 | 说明 |
|---|---|---|---|
| G1 | 只处理 seg.type==='image' | src/index.ts:539-579 | mface / marketface 段完全没有下载逻辑，渲染侧也只落 [未知消息段:mface]（wakeup.ts:488-495 无 mface case） |
| G2 | 只有 data.url 是 http(s) 才下载 | src/index.ts:549-551 | url 缺失 / file:// / 本地路径 → 直接跳过，无 get_image / get_file 兜底 |
| G3 | 失败只 logger.debug | src/index.ts:575-577 | 线上零可见性，44% 失败率长期无人发现，也无法事后定位 |
| G4 | 离线同步只入库不落盘 | src/gateway/sync.ts:127 | 停机期间的消息 local_path 永久为 null |
| G5 | 群聊下 fetch_chat_resource 误判 | src/tools/index.ts:136-152 | 只要 peer 以 group_ 开头就当成"群文件"，图片/表情的 file_id 会被路由到 get_group_file_url 并因缺 busid 直接报错 → 群里模型想补拉图片基本走不通 |
| G6 | 引用消息兜底回填脏数据 | src/index.ts:854-874 | local_path 写 quotedImages[0]（可能是 URL 或裸文件名）、type 被降级为 'text'，会覆盖成非路径本地值 |

## 3. 修复方案（建议按 P0→P3 分批，每批 TDD 先行）

### P0 可观测性（✅ 已完成，见 §6 实施记录）
- src/index.ts 下载失败日志由 debug 提到 warn，附带 msg_id / peer / file_id / url 前缀 / HTTP status / 响应体前 120 字符（脱敏，不落 rkey 全量）。
- 新增「落盘健康度」周期汇总（成功/失败/跳过 计数），便于线上观测一轮再定后续。
- 契约测试：构造 fetch 返回 400 的桩，断言 warn 日志被调用且字段齐全。

### P1 后缀真值化（问题 1）
- MediaStorageManager.saveBuffer：**魔数优先级与 type 解耦** —— 只要 detectedExt 存在就纠正 filename 后缀（含 files 类型）；detectedExt 缺失时才保留原后缀。
- fetch_chat_resource / downloadPrivateFile：不再把 data.file（QQ 的 MD5.jpg 伪名）当权威后缀，仅作 filename 展示用，后缀一律以字节为准。
- 存量自愈：一次性扫描/迁移（对齐 face-migration.ts 的做法），把 downloads/ 与 faces/ 中后缀≠魔数的文件改名，并同步 messages.local_path / messages.content / faces.format / faces.file_path。
- 契约测试（红→绿）：saveBuffer({type:'files', filename:'x.gif'}, jpegBytes) → .jpg；collectFace 对错后缀文件应写入真实 format。

### P2 元信息进模型输入（问题 2）
- 让 payload.images 真正进入模型输入：dispatchWakeup 除 text 段外，按 payload.images 追加 image 段（或至少在文本中列出"随消息附带的本地图片路径"），不再依赖 content 字符串。
- parseNormalizedContent 的图片/表情占位补全元信息：[表情包:<summary> | 文件ID:<file_id> | 已保存:<path> | 未落盘]，保证模型**总能拿到 file_id**，可精确补拉而不是猜。
- updateLocalPathByFileId 增加 content 回写（把 已保存: path 补进 content），消除"拉过但历史仍是空"。
- 契约测试：无路径表情包 → content 必含 file_id 且标注未落盘；补拉后 content 含路径。

### P3 无条件落盘补全（问题 3）
- G1：onMessage 增加 mface / marketface 分支（无直链则登记待补拉，不静默丢）；parseNormalizedContent 增加 mface 渲染（[商城表情:<summary>]）。
- G2：url 缺失时走 NapCat 兜底（get_image / get_file → 本地路径 → mediaManager 落盘），失败才标记 dl_failed。
- G3：带指数退避的重试（1~2 次即可，避免放大 CDN 压力；兼顾并发失败率 19% 的观测结果）。
- G4：OfflineMessageSyncer 对**最近 24h / 最近 N 条**的媒体做一次性补落盘（全量补会短时间内狂拉 CDN，需你拍板范围）。
- G5：fetchChatResource 的群文件判定改为「落库 type==='group_file' 或有 busid」优先，image / sticker 一律走媒体下载路径。
- G6：引用兜底回填只写真实存在的本地路径，绝不写 URL / 裸文件名，且不把 type 降级为 text。

## 6. P0 实施记录（已完成，2026-10-30）

> 用户拍板：先断点插桩、跑一段时间看数据再继续改；日志**不进控制台**（DSH 插件没有控制台），落盘到数据目录、文件名带时间。

### 6.1 落盘位置与格式
- 目录：`<DSH_HOME>/napcat/logs/`（与 `messages.sqlite`、`downloads/` 同根，按 `resolveDshPath` 规则；生产实机为 `%USERPROFILE%\.dsh\napcat\logs`）。
- 文件：`media-YYYYMMDD.log`（每日一个，文件名携带日期），单文件 8MB 上限，保留 14 天（按文件名日期清理）。
- 格式：JSONL，一行一个事件，首字段 `ts`（本地时区 ISO，带偏移）+ `level` + `event`。
- 隐私：url 一律只记 `url_host` / `url_has_rkey`，错误文本里的 URL 走 `redactUrls()` 替换为 `https://<host>/<redacted>`。

### 6.2 埋点清单（事件名）

| 事件 | 级别 | 关键字段 | 用途 |
|---|---|---|---|
| `image_seen` | info | file_id / is_sticker / summary / sub_type / file_size / has_url / url_host / url_has_rkey | 成功率分母 |
| `image_saved` | info | path / dedup_level / bytes / duration_ms / url_host | 成功率分子 + 去重命中 |
| `image_failed` | warn | error_name / error / http_status / body_head / url_host / duration_ms | 失败真实原因（关键） |
| `image_skip` | warn | reason(no_url / non_http_url / no_media_manager) | 未尝试下载 |
| `mface_seen` | info | summary / emoji_id / emoji_package_id / data_keys | 商城表情频次与字段形态 |
| `file_saved` / `file_failed` | info/warn | via / path / error | 私聊文件落盘（同主题顺带观测） |
| `fallback_result` | info/warn | api / ok / retcode / wording / has_path / path_exists / has_url / url_host / duration_ms | **get_image / get_file / get_msg 逐版本可用性** |
| `fallback_skipped` | info | reason(no_gateway / no_file_id / no_msg_id / api_unavailable) | 无法探测的原因 |
| `fallback_throttled` | warn | max_per_minute | 限流（默认 20 次/分钟） |
| `sync_media_no_path` | info | peer / inserted / media_no_path | 离线补拉带来的无路径媒体量 |
| `fetch_route` | info | route(group_file/media) / has_busid | G5 群聊误路由的真实现状 |
| `fetch_result` | warn | route / ok / error | 补拉失败归因 |

### 6.3 兜底探测策略（只观测，不落盘）
失败/跳过时按 `get_image({file})` → `get_file({file_id})` → `get_msg({message_id})` 顺序探测；
每条结果都记 `fallback_result`，含 `path_exists`（NapCat 返回的本地路径在本机是否真的存在）与 `has_url`。
探测为**fire-and-forget**（不阻塞消息主链路），且每分钟最多 20 轮，超限记 `fallback_throttled`。
