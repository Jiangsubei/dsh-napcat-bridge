# 根因分析与修复报告：后台回顾与 QQ 会话掉入 WebUI "未分组" 缺陷

> **报告编号**：BUG-20261022-UNGROUPED  
> **涉及模块**：`src/gateway/session.ts`, `src/gateway/session/persistence.ts`, `src/gateway/session/workspace.ts`, `src/memory/review.ts`  
> **基准版本**：DeepSeek Harness `0.2.1-rc.2`  
> **编写日期**：2026-10-22  

---

## 1. 现象描述

用户真机运行与截图中暴露如下异常现象：
1. QQ 会话（如 `私聊: 我也要做吗 1000000001 #1`，对应 ID `qq-user-1000000001`）在触发后台记忆回顾（Background Review）或交互过程中，被从 `NapCat` 顶级工作区中剔除，掉落到 DSH Web UI 的 **“未分组” (Ungrouped)** 区域；
2. 同时生成了新的会话 `qq-user-1000000001-2`（#2）留在 `NapCat` 工作区下，用户原有的上下文遭到割裂。

用户反馈定位线索：“可能是触发了 background review，然后这个会话到未分组去了。你看看是不是这个原因，一起查一下。”

---

## 2. DSH 0.2.1-rc.2 原生架构对照与根因深度剖析

对照本地 `node_modules/@deepseek-ai/dsh-workspace/lib/index.js` 及 `dsh-session-persistence-jsonl` 源码核查，DSH 的工作区会话归属机制如下：

### 2.1 DSH 0.2.1 的工作区准入判定机制 (`candidateMatches`)
在 `@deepseek-ai/dsh-workspace` 中：
```javascript
// WorkspaceRegistry.host
candidateMatches: (id, path) => this.sessionPaths.get(id) === path || this.missingSessionPaths.has(id)

// WorkspaceEntity
get sessionIds() {
  return this.record.sessionIds.filter((id) => this.host.candidateMatches(id, this.record.path));
}

async mutate(fn) {
  let next = await this.host.table().update(this.id, (current) => {
    const changed = fn(current);
    const sessionIds = changed.sessionIds.filter((id) => this.host.candidateMatches(id, changed.path));
    if (changed === current && sessionIds.length === current.sessionIds.length) throw unchangedSentinel;
    return {
      ...changed,
      sessionIds,
      updatedAt: new Date().toISOString()
    };
  });
  this.record = next;
}
```
**致命特性**：
在 DSH 0.2.1 中，无论是读取 `workspace.sessionIds` 还是执行任何工作区变更 `mutate()`（包括 `attachSession`、`detachSession`），DSH 都会使用 `candidateMatches` 过滤整个工作区的所有会话。
只要某个会话在 `workspaceRegistry.sessionPaths` 映射表中不存在，或其路径与工作区路径不匹配：
`mutate()` 会**立即且不可逆地将该会话从持久化工作区记录 (`record.sessionIds`) 中剔除**！而在 DSH 前端看来，任何不属于任何工作区的会话，一律自动归类到 **“未分组” (Ungrouped)**。

### 2.2 根本原因链路还原

导致该缺陷的完整时序与因果链条如下：

1. **`isSessionPhysicallyPresent` 的纯磁盘扫描缺陷**：
   - DSH 0.2.1 中 `sessionPersistence` 采用惰性物化机制（Lazy Materialization），会话在首次 append/flush 之前仅存在于进程内存中。
   - `persistence.ts` 的 `isSessionPhysicallyPresent` 仅检测磁盘文件，未检查 `ctx.sessions?.get(sessionId)` 或 `ctx.agents?.get(sessionId)`；
   - 当遇到网络拥塞、Turn 中途报错（如用户本次第一轮遇到的 `Connection error. TRANSPORT`）或尚未刷盘的时序时，`isSessionPhysicallyPresent` 误判该活跃会话为“物理不存在”；
2. **`session.ts:335` 的越权删除私有状态**：
   - 在 `peerToSessionId` 中，代码在扫描 `wsRegistry.headers` 时，一旦上述误判发生，错误执行了：
     ```typescript
     wsRegistry.sessionPaths?.delete?.(sid);
     wsRegistry.headers.delete(sid);
     ```
   - 此操作暴力抹除了 DSH 核心 `workspaceRegistry` 对该会话目录的内存记账；
3. **后台回顾 (Background Review) 触发与时序放大**：
   - 当该会话触发后台回顾时，`review.ts` 先调用 `parentWorkspace.attachSession(reviewSessionId)`，回顾结束用完即焚调用 `parentWorkspace.detachSession(reviewSessionId)`；
   - 这两个调用均会触发 `parentWorkspace.mutate()`；
   - 在 `mutate()` 执行时，DSH 重新校验工作区内所有会话的 `candidateMatches`；
   - 由于父会话 `qq-user-1000000001` 刚刚在第 2 步被抹掉了 `sessionPaths`，`candidateMatches` 判定失败；
   - DSH 原生机制立即将父会话从 `NapCat` 工作区的 `sessionIds` 物理持久化列表中剔除，父会话落入 **“未分组”**！
4. **编号递增与新会话生成**：
   - 随后的消息入站时，`peerToSessionId` 由于原会话被标记为“物理失效”且未在工作区找到，误触发了编号递增，从而新建了 `qq-user-1000000001-2` 并挂载至 `NapCat`。

用户的直觉完全正确：**正是后台回顾的挂载与清理触发了工作区 `mutate()`，使得因误删 `sessionPaths` 的父会话被 DSH 原生安全过滤器永久踢到了未分组。**

---

## 3. 修复方案与工程落地

根据上述确凿事实，我们执行了闭环整改：

### 3.1 废除越权删除私有缓存 (`src/gateway/session.ts`)
- 彻底移除 `peerToSessionId` 中针对 `wsRegistry.sessionPaths.delete`、`headers.delete` 和 `invalidSessionPaths.delete` 的越权操作；
- 桥接严禁干涉 DSH 工作区内部私有索引生命周期。

### 3.2 内存活跃先行判定 (`src/gateway/session/persistence.ts`)
- 在 `isSessionPhysicallyPresent` 中优先检查 `this.ctx.sessions?.get(sessionId)` 与 `this.ctx.agents?.get(sessionId)`；
- 确保正在内存中活跃、或处于交互中但尚未落盘的 live 会话，100% 被判定为有效存在，杜绝假死误判；
- 隔离 `checkRoots`，仅在未指定自定义 `dshHome` 时回退至全局目录。

### 3.3 登记与路径记忆加固 (`src/gateway/session/workspace.ts`)
- 在 `registerWorkspace` 挂载会话时，主动向 `wsRegistry.sessionPaths` 补充登记规范路径；
- 解决 DSH `attachSession` 在会话已存在于 `record.sessionIds` 时跳过 `rememberSessionPath` 的边界陷阱。

### 3.4 后台回顾时序防御与父会话工作区防护 (`src/memory/review.ts`)
- **前置防护**：在 `runReview` 挂载 `reviewSessionId` 前，显式加固登记 `parentSessionId` 的 `sessionPaths`；
- **清理防护**：在 `cleanupReviewSession` 执行 `detachSession` 之前，强制同步父会话的 `sessionPaths` 规范路径，并在所有工作区 `detachSession` 完成之后才清除临时 review 会话的私有映射；
- **防误删防护**：加固 Step 6 物理删除，防止 `parentSession` 入参误传导致误伤父会话物理目录。
