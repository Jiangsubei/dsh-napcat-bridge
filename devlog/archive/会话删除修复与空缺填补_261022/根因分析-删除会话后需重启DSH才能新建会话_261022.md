# 根因分析：Web/桌面端删除会话后需重启 DSH 才能新建会话之缺陷考证

- **日期**：2026-10-22
- **责任模块**：`src/gateway/session.ts`（SessionManager 寻址与句柄生命周期）
- **状态**：根因已彻底查明，待用户确认修复方案

---

## 1. 结论

**用户的直觉与判断完全正确！**

当用户在 Web 或桌面端删除了会话后，磁盘上的物理会话目录与日志文件确实已被清理；但在当前 DSH 进程的内存中，NapCat 插件（以及 DSH 宿主内核）依然缓存了该会话的写句柄（`AgentHandle`）与 Agent 实例。  
当 QQ 收到新消息时，网关的寻址逻辑**误把内存中的残留句柄当作物理文件存在**，从而将消息投递给了一个“磁盘上已不存在的僵尸会话”；底层持久化写入异常被内核吞掉，导致 QQ 端**永远等不到回复**，且无法自动创建新会话；直到用户**彻底重启 DSH**、内存完全重置后，冷启动下的物理检测才会真正去探测磁盘文件，从而恢复正常新建会话。

## 3. 代码深层证据与缺陷剖析

### 缺陷 1：`isSessionPhysicallyPresent` 混淆了“内存存活”与“物理存在”（致命根因）
- **位置**：`src/gateway/session.ts:492-496`
- **代码**：
  ```typescript
  isSessionPhysicallyPresent(sessionId: string): boolean {
    if (this.activeHandles.has(sessionId)) return true; // ⚠️ 致命缺陷
    const live = (this.ctx.get('sessions') || (this.ctx as any).sessions)?.get?.(sessionId);
    if (live) return true; // ⚠️ 致命缺陷
    ...
  ```
- **分析**：
  函数的职责是“检查物理磁盘中是否存在”，但它前两行却直接根据**内存中的 `activeHandles` 或 `ctx.sessions`** 盲目返回 `true`。
  一旦一个会话在此前被 QQ 访问过，`this.activeHandles.has(sessionId)` 就永远为 `true`。即使会话在磁盘上已被彻底粉碎，该函数依然坚定地向系统谎称该会话“物理存在”。

### 缺陷 2：`activeHandles` 内存句柄只进不出，缺乏物理失效清理机制
- **位置**：`src/gateway/session.ts:1081-1092`
- **分析**：
  在 `SessionManager` 中，`activeHandles` 一旦通过 `agents.create` 或 `agents.resume` 创建后，只有在 `isSessionArchived(sessionId)`（DSH 官方归档）为 `true` 时才会被 `dispose()` 并从 Map 中删除；
  而整个项目中 `releaseActiveHandle()` 没有任何业务路径在调用！
  当用户在桌面端操作的是**物理删除**（而非 DSH 归档 `archiveSession`）时，`isSessionArchived` 判定为 `false`，该句柄将**永久滞留在内存中**。

### 缺陷 3：`getOrCreateAgent` 盲目复用内存中的僵尸 Handle
- **位置**：`src/gateway/session.ts:1081-1105`
- **代码**：
  ```typescript
  if (this.activeHandles.has(sessionId)) {
    const handle = this.activeHandles.get(sessionId)!;
    if (!this.isSessionArchived(sessionId)) {
      // ⚠️ 只要没被归档，根本不确认磁盘文件在不在，直接复用已死亡的 Agent
      return handle.agent;
    }
  }
  ```
- **分析**：
  唤醒时，网关直接把消息塞给这个底盘已经被抽走的僵尸 Agent；AgentLoop 启动后无法持久化，在 `kick()` 异常中静默失败，消息如泥牛入海，QQ 端永远等不到任何出站回复。

### 缺陷 4：空目录误判（文件系统探测漏洞）
- **位置**：`src/gateway/session.ts:543`
- **代码**：
  ```typescript
  if (hasLog || files.length === 0) return true; // ⚠️ files.length === 0 判定为存在
  ```
- **分析**：
  若桌面端删除会话时删除了日志文件，但留下了一个残留的空文件夹，代码竟然直接判定空目录也是“物理存在”，导致哪怕冷启动也可能被误判。

## 4. 为什么是“有概率”，而不是 100% 发生？

用户观察到的“**有概率**需要重启”，与以下三个边界分支高度吻合：

1. **概率分支 A（命中 Bug）**：
   该会话在当前 DSH 运行期间**已经由 QQ 触发过对话**。此时 Bridge 内存中持有 `activeHandles`；用户在桌面端物理删除了该会话后，QQ 再次发消息，100% 命中上述僵尸句柄复用缺陷，**必须重启 DSH**。
2. **概率分支 B（未命中 Bug，直接正常新建）**：
   DSH 刚启动，QQ **未曾与该会话发生交互**（`activeHandles` 为空，内存未加载）。用户在桌面端删除了会话。当 QQ 第一次发来消息时，内存中无残留，`isSessionPhysicallyPresent` 真正穿透到文件系统检测返回 `false`，从而**自动调用新建逻辑，无需重启**。
3. **概率分支 C（未命中 Bug，直接走归档新建）**：
   用户在桌面端使用的操作如果是 DSH 的标准“归档（Archive）”而非“物理删除”，`workspaceRegistry.archivedSessionIds` 会包含该会话，此时代码中的 `isSessionArchived` 能正确拦截并走新轮次算法，**无需重启**。

## 5. 修复方案设计与决策

为了彻底杜绝该缺陷，需执行以下修复：

1. **改造 `isSessionPhysicallyPresent`**：
   - 彻底移除对 `activeHandles.has` 与 `ctx.sessions.get` 的短路；
   - 必须以物理磁盘上的真实日志文件（`session.v3.jsonl.zstd` / `session.v2.jsonl` 等）为唯一物理存在依据；
   - 移除 `files.length === 0` 的空目录误判。
2. **在 `getOrCreateAgent` 建立物理存活二次确认与僵尸句柄淘汰机制**：
   - 在复用 `activeHandles` 或 `agents.get` 之前，必须执行 `isSessionPhysicallyPresent(sessionId)`；
   - 若发现物理磁盘已不存在，立即调用 `handle.dispose()` 释放内核锁与上下文，从 `activeHandles` 与 `peerCurrentSessionId` 中剔除；
   - 联动清理 SQLite 数据库中已失效的 `current_session_id`；
   - 重新计算可用新 SessionId，走全新的 `agents.create` 流程。
3. **编写契约测试保护**：
   - 模拟“内存持有 handle 但物理目录被 rm”的场景，断言 `dispatchWakeup` 能够自动淘汰僵尸句柄并创建全新会话，QQ 消息正常得到回复。
