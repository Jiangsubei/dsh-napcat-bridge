## 二、前置核实 1：`sessionController.cancel` 签名与机制

### 2.1 源码查验结果

1. **Host 侧服务定义 (`@deepseek-ai/dsh-api-session-controller`)**：
   - 服务注册名：`'sessionController'`，Wire 命名空间：`'session'`。
   - 类定义位于 `dsh-api-session-controller/lib/index.js`（line 2598 & 2797）与 `lib/types/index.d.ts`（line 145）：
     ```ts
     export declare class SessionController extends TypertRemoteService {
       cancel(request: SessionCancelRequest): SessionCancelValue;
     }
     ```
   - 请求体与返回体定义位于 `lib/types/types.d.ts`（line 318-323）：
     ```ts
     export interface SessionCancelRequest {
       readonly sessionId: SessionId;
     }
     export interface SessionCancelValue {
       readonly accepted: true;
     }
     ```
   - Host 核心实现逻辑（`lib/index.js` line 831-837）：
     ```js
     cancel(request) {
       const agent = this.ctx.agents.get(request.sessionId);
       if (agent === void 0) {
         throw new RemoteError("session/not-found", `session "${request.sessionId}" not found (not attached)`, { sessionId: request.sessionId });
       }
       if (hasApiSessionSubagentOwner(this.ctx, agent.session, agent)) {
         throw apiSessionSubagentOwnershipError(request.sessionId);
       }
       agent.cancel({ kind: "user" }, { keepInbox: true });
       return { accepted: true };
     }
     ```

2. **Client 侧封装 (`lib/client.js`)**：
   - 在前端 `ClientSession` 类中（line 987）：
     ```js
     async cancel() {
       const address = this.address;
       const result = address !== void 0
         ? await this.remote.subagents.interruptByParent(address.childSessionId, address.parentSessionId, "continuable")
         : await this.remote.session.cancel({ sessionId: this.sessionId });
       if (!result.ok) {
         this.promptError = { op: "stop", error: result.error };
         this.notifier.markDirty();
       }
       return result;
     }
     ```
   - 前端对象上的 `session.cancel()` 为无参方法，但底层 RPC 依然转换为 `remote.session.cancel({ sessionId: this.sessionId })`。

### 2.2 结论与设计选型
- **在 NapCat 插件环境中**：插件运行在 Host 侧 Cordis Context，从 `context.ctx.get('sessionController')` 获取的是 Host 的 `SessionController` 服务实例。
- **确切签名**：
  ```ts
  await sessionController.cancel({ sessionId: context.session.id });
  ```
- **异常与边界情况处理**：
  - 若 `sessionController` 服务未注册（例如在未加载 web-app 的极简单测环境中）：提示 `sessionController 服务不可用`；
  - 若 Agent 尚未创建或未 attach：Host 会抛出 `RemoteError("session/not-found")`，命令捕获后输出友好提示；
  - 若 Agent 处于空闲状态（当前未在生成）：底层 `agent.cancel` 执行时会判断 `if (this.phase.kind !== "idle")`，在 idle 状态下安全空转无副作用，正常返回 `{ accepted: true }`。

## 三、前置核实 2：`dsh-token-meter` 的 `measure(session)` 与 `requestHeader`

### 3.1 源码查验结果

1. **`measure()` 方法签名（`dsh-token-meter/lib/types/index.d.ts` line 45）**：
   ```ts
   measure(session: Session, requestHeader?: EpochHeader): TokenMeasurement;
   ```
2. **内部执行逻辑（`dsh-token-meter/lib/index.js` line 620-622）**：
   ```js
   measure(session, requestHeader) {
     const state = this._sync(session);
     const header = requestHeader === void 0 ? state.header : canonicalHeader(requestHeader);
     const pricing = this._routeImagePricing(header);
     const surface = priceSurface(state.surface, pricing);
     const anchor = state.anchor;
     // ... 计算 baseline 与 totalTokens ...
     return deepFreeze(structuredClone({
       logRevision: state.consumedEvents,
       baseline,
       surfaceDeltaTokens,
       totalTokens: Math.max(0, baseline.tokens + surfaceDeltaTokens),
       surfaceTokens: surface.surfaceTokens,
       nodes: surface.nodes
     }));
   }
   ```
3. **是否需要显式传 `requestHeader`**：
   - **不需要**。当 `requestHeader` 为 `undefined` 时，`measure()` 内部自动使用 `state.header`。
   - `state.header` 在会话事件日志被 `_sync(session)` 折叠时，自动从最新一条 `request/header` 事件提取。
   - 若会话为全新未对话会话（无历史请求），`state.header` 为 `undefined`，`baseline` 为 `{ kind: 'none', tokens: 0 }`，`totalTokens` 表现为 0。

### 3.2 关键结构限制：`measure().nodes` 不包含系统提示词和工具
- `TokenMeasurement.nodes` 数组包含的是当前会话可见的**对话消息节点（surface nodes）**：
  ```ts
  export interface TokenSurfaceNode {
    readonly seq: SessionSeq;
    readonly tokens: number;
    readonly heuristicTokens: number;
  }
  ```
- **系统提示词（System Prompt）和工具声明（Tools）并不在 `nodes` 里**，它们属于 `header`（在底层由 `estimateSystemTokens(header)` 和 `estimateToolsTokens(header)` 估算计价）。
- 因此，不能仅凭遍历 `nodes` 拆分出系统提示词和工具。

## 四、前置核实 3：上下文上限 `contextWindow` 与分段明细来源

### 4.1 Web UI 的实现标准（`dsh-client-ui-conversation`）

在 WebUI 源码 `dsh-client-ui-conversation/lib/client.js`（line 14880-15049）中，上下文用量组件 `ContextMeter` 并不是直接调用 `measure()` 拆分，而是读取了两个官方会话投影（Session Projections）：
1. **`contextPressure` 投影**（由 `dsh-token-meter/src/usage-projection.ts` 维护）：
   ```ts
   export interface ContextPressureProjection {
     pressureTokens?: number;   // 提供方报告的最新请求提示词大小
     projectedTokens?: number;  // 下一请求预计 token 用量
     contextWindow?: number;    // 当前模型路由的上下文上限容量
   }
   ```
   - 其百分比算法与 WebUI 一致：
     ```ts
     const usedTokens = pressure?.projectedTokens ?? pressure?.pressureTokens;
     const percent = Math.min(100, Math.round(usedTokens / pressure.contextWindow * 100));
     ```
2. **`contextBreakdown` 投影**（由 `dsh-token-meter/src/breakdown-projection.ts` 维护）：
   ```ts
   export interface ContextBreakdownProjection {
     systemTokens: number;  // 系统提示词 token
     toolsTokens: number;   // 工具 schema token
     messageTokens: number; // 对话消息 token
   }
   ```
   - 对应 WebUI 面板显示的 3 行：
     - `context.system` -> `系统提示词`
     - `context.tools` -> `工具`
     - `context.messages` -> `对话消息`

### 4.2 `contextWindow` 的获取优先级方案
为确保在各种装配环境（有无投影服务、真实运行时、单测 mock 环境）下都能稳定获取到 `contextWindow`，采用双重解析方案：
1. **第一优先级（投影优先）**：
   从 `ctx.get('sessionProjections')?.snapshot(session, ['contextPressure'])?.values?.contextPressure?.contextWindow` 直接读取。
2. **第二优先级（LLM 模型元数据）**：
   若投影未提供或未加载，从会话当前选中的模型获取：
   - 通过 `context.sessionManager?.getModelSelection(context.session.id)` 或 `agent.modelSelection?.current` 获取 `(provider, model)`；
   - 调用 `ctx.get('llm')?.resolveModel(provider, model)` 获取 `LlmResolvedModelInfo`，其 `info.context?.contextWindow` 即为模型规格声明的上下文窗口（如 1048576 对应 1M）；
   - 或从 `ctx.get('llm')?.discoveredModels()` / `getDiscoveredModels(ctx)` 匹配 `m.contextWindow`。
3. **保底兜底**：
   若均未获取到 `contextWindow`，严格按照任务包要求：**不显示百分比与上限，仅显示 `totalTokens`**。

### 4.3 分段明细的获取与降级方案
1. **第一优先级**：读取 `sessionProjections.snapshot(session, ['contextBreakdown'])`，获得 `systemTokens`、`toolsTokens`、`messageTokens`。
2. **第二优先级（降级）**：
   若无 `sessionProjections` 服务，则通过 `tokenMeter.measure(session)` 获取：
   - `messageTokens = usage.surfaceTokens`；
   - 若 `usage.totalTokens > usage.surfaceTokens`，差额归为 header 提示词与工具；
   - 若全部为 0，展示 0 或总用量。

### 4.4 Token 数字紧凑格式化算法（对齐 WebUI `formatTokens`）
WebUI `formatTokens` 算法规则：
- `< 1000`：直接显示数字，如 `850`
- `< 1,000,000`：除以 1000，`>= 100` 四舍五入到整数，`< 100` 保留 1 位小数，加上 `K`（如 `1.7K`, `17K`, `250K`）
- `>= 1,000,000`：除以 1000000，类似规则加上 `M`（如 `1M`, `1.2M`）

## 五、`/resume` 与 `SessionManager` 实现确认

1. **`listPeerSessionIds(peer: string): string[]`**：
   - 解析 peer 的 baseId（群聊 `qq-group-<id>`，私聊 `qq-user-<id>`）；
   - 扫描 `workspaceRegistry.headers.keys()` 与 SessionManager 内部跟踪/DB 的会话 ID；
   - 用 `parseSessionId(sid)` 提取 `round` 与 `version` 并校验同 base；
   - 过滤条件：`isSessionPhysicallyPresent(sid)` 且 `!isSessionArchived(sid)`；
   - 排序规则：按 `(round, version)` **升序**（旧→新）返回。
2. **`/resume` 命令渲染**：
   - 倒序渲染列表：最新会话在最上方，编号为 `sessions.length`；最旧会话在最下方，编号为 `1`；
   - 接受参数 `idx`：用户输入 `1` 对应 `sessions[0]`（最旧），输入 `N` 对应 `sessions[N-1]`（最新）；
   - 越界检查：`idx < 1 || idx > sessions.length` 返回范围错误提示。
3. **`resumeSession(peer: string, sessionId: string): boolean`**：
   - 校验目标会话物理存在且未归档；
   - 更新 `peerCurrentSessionId.set(peer, sessionId)`；
   - 更新 `clearedVersions.set(peer, { round, version })`；
   - 更新 `db.saveSessionState` 持久化；
   - 返回 `true`。后续发消息时 `peerToSessionId` 会优先取 `peerCurrentSessionId` 缓存，实现后续消息精确路由至已恢复会话。

## 六、总结与汇报建议

1. `sessionController.cancel` 确切签名为 `sessionController.cancel({ sessionId: context.session.id })`，返回值 `{ accepted: true }`，完全契合 Host 架构。
2. `tokenMeter.measure(session)` 不需要传 `requestHeader`，内部会自动回放并使用最新事件的 header。
3. `contextWindow` 与分段明细优先由 `sessionProjections` (`contextPressure` / `contextBreakdown`) 提供，以 `llm.resolveModel` / `discoveredModels` 作为 capacity 的可靠二级补充，完美对齐 Web UI 的展示。
4. 所有 API 签名与数据流闭环均已在 DSH 运行时源码得到确凿证实，可以进入实现阶段。
