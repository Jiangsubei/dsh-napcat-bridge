# 任务包：修复主动触发回复引用/艾特陈旧消息（poke + 潜水唤醒）

> **项目**: dsh-napcat-bridge  
> **日期**: 2026-09-06  
> **优先级**: P1  
> **一句话**: 无真实入站消息的主动触发（戳一戳 poke、潜水超时 idle 冒泡）触发的回复，出站 quote/at 会回退到**上一条真实消息（消息 A）**的上下文，导致引用/艾特永远落在 A 上。修复为：这类触发回复**不引用也不艾特**，仅纯文本。

---

## 1. 根因（已探索确证）

**链路**：
1. `dispatchWakeup`（session.ts:818）只 `agent.followup(userMsg)` 创建消息并推给 agent，**不设置任何 outbound inbound 上下文**
2. 回复出站时，`buildMessagePayload`（stream.ts:266）取 `inbound = turnContexts[peer][turn] || inboundContexts.get(peer)`
3. poke / idle 的回复没有 turn 绑定，回退到 `inboundContexts.get(peer)`——它仍是**上一条真实消息 A** 的上下文（`msg_id`=A、`from_user`=A 的发送者）
4. `buildMessagePayload`（stream.ts:276-281）：`quote_original && inbound.msg_id` → CQ:reply 引用 A；`at_questioner && inbound.from_user` → CQ:at 艾特 A 的发送者

**为什么 poke 没覆盖 A**：index.ts:690 `msgIdFromEvent = Number(event.message_id)`，poke 是 notice 事件**无 message_id** → NaN → `replyContext = undefined` → `trackInboundContext` 被跳过。
**为什么 idle 也没覆盖**：idle 走定时器直接 `dispatchWakeup(payload)`（proactive.ts:138），根本不经过 index.ts:678 的 replyContext 路径。

> `stableNoticeMsgId`（index.ts:61）只在 `db.saveMessage` 落库时给 poke 造合成 msg_id，**没进出站 inbound**，故无关。

## 2. 受影响触发（已排查）

| 触发 | from_user | msg_id | 现状 | 修复目标 |
|---|---|---|---|---|
| poke 戳一戳 | 无 | 无 | 引用/艾特陈旧 A | 不引用不艾特 |
| idle 潜水超时（暖群冒泡） | `''` | 无 | 引用/艾特陈旧 A | 不引用不艾特 |
| random 概率唤醒 | 有（真实消息） | 有（真实 message_id） | ✅ 正确 | 不变 |
| group_upload / 撤回 | — | — | 不触发回复 | 不变 |

## 3. 修复设计（定稿）

### 3.1 核心：给"无真实入站消息"的触发注册空白 inbound 上下文

在 `dispatchWakeup` 之前/内部，对**没有 msg_id 的触发**（poke、idle），调用：

```ts
outboundBridge.trackInboundContext(peer, {
  msg_id: undefined,
  from_user: '',
  trigger: 'poke' | 'idle',   // 标注触发来源，便于诊断
});
```

- `buildMessagePayload` 判断 `inbound.msg_id` / `inbound.from_user` 为空 → **不 push reply/at** → 纯文本
- **覆盖陈旧 A**：后续 poke / idle 回退到空白上下文，不再引用/艾特 A
- 下一条**真实消息**进来会正常覆盖 → 恢复引用/艾特

**落点（实现时核实）**：
- poke：在 index.ts poke 唤醒分支（~787-825）确认 wakeup 后补充注册空白上下文
- idle：在 proactive.ts checkIdleGroups 调 `dispatchWakeup` 前，或 dispatchWakeup 内部统一处理（`payload.from_user 为空且无 msg_id` → 注册空白上下文）

建议在 **`dispatchWakeup` 内部统一做**（集中一个点），判断：payload 无 msg_id（或 from_user 为空）→ 先 `trackInboundContext(peer, 空白上下文)` 再 followup。这样 poke / idle 一处修复全覆盖，未来其它无消息触发也自动安全。

### 3.2 加固（可选，建议做）：buildMessagePayload 兜底不跨触发复用

`stream.ts:266` `inboundContexts.get(peer)` 兜底是"跨触发复用陈旧上下文"的温床。加固为**只在明确绑定当前触发的 inbound 时引用/艾特**；无有效绑定则纯文本。

- 实现方式（实现期选定）：
  - 方案 1：`buildMessagePayload` 增加参数显式传本次 inbound；无有效 msg_id/from_user 就不加 reply/at（即使兜底池里有）
  - 方案 2：`inboundContexts` 条目带 `trigger` 与 `expiresAt`（或绑定 expectTurn），跨触发生效前校验
- 目标：即使漏注册空白上下文，也不会因陈旧 fallback 出错引用/艾特

## 4. 任务拆解（原子提交）

1. **dispatchWakeup 统一空白上下文**：无有效 msg_id/from_user 的唤醒 → 先注册空白 inbound 上下文（覆盖 poke + idle；随机/真实消息不受影响）
2. **buildMessagePayload 加固**（3.2）：跨触发不复用陈旧 inbound 引用/艾特（保底防御）
3. **契约测试**：
   - poke 唤醒回复不含 CQ:reply / CQ:at（纯文本）
   - idle 唤醒回复不含 CQ:reply / CQ:at（纯文本）
   - 真实消息唤醒仍含引用/艾特（按 quote_original/at_questioner 配置）——**不被误伤**
   - 连续多次 poke 回复均不引用不艾特（覆盖"永远 A"场景）
   - poke/idle 之后下一条真实消息恢复引用/艾特
4. **README**（如需）：行为说明"戳一戳/潜水暖群不引用不艾特"
