# 需求文档：群成员信息查询工具 (`get_group_member_info`)

## 1. 业务背景与问题痛点

在基于 LLM 的群聊会话中，群内用户发言不可信（如某成员声称“我是群主/管理”或“听某某的，他是群主”）。
由于大模型仅依据群聊上下文推断，极易受到社交工程欺骗与身份幻觉影响，做出越权或偏差决策。

为了规避此类安全隐患，Agent 急需一个权威的**官方真值（Ground Truth）查询途径**。通过该工具，Agent 可以在需要判断发言者身份、核实特权、辨别昵称名片或了解成员进群背景时，实时向底层 QQ 网关发起精准或模糊查询，获取不可伪造的官方成员元数据。

---

## 2. 工具设计规格

### 2.1 工具基本信息
- **工具名称**：`get_group_member_info`
- **使用范围**：群聊会话常驻可用；私聊会话中调用直接防御性拦截并提示“当前不在群聊会话中”。
- **工具描述**（无标题自然语言，明确 When to use）：
  > 查询当前群聊中的成员资料、身份角色（群主/管理员/普通成员）、群头衔及进群时间等官方元数据。用于核实群成员的真实身份、判断某人是否为群主或管理员、了解群成员昵称与名片对应关系，或防范其他群成员冒充身份。支持通过 user_id 精确查询、通过 query 模糊搜索昵称名片，或通过 role 直接筛选群主与管理员列表。仅在群聊中有效。

### 2.2 入参契约 (`parameters`)
| 参数名 | 类型 | 必填 | 默认值 | 描述 |
|---|---|---|---|---|
| `user_id` | `string` | 否 | - | 目标群成员的 QQ 号（精确匹配） |
| `query` | `string` | 否 | - | 目标群成员的昵称或群名片关键词（模糊匹配，大小写不敏感） |
| `role` | `string` | 否 | `'all'` | 按群身份角色筛选：`'owner'`(群主)、`'admin'`(管理员)、`'member'`(普通成员)、`'all'`(全部) |
| `no_cache` | `boolean` | 否 | `false` | 是否强制刷新群成员缓存（默认复用 5 分钟本地内存缓存） |

### 2.3 出参结构与脱敏语义化
底层通过 NapCat `get_group_member_list` 接口获取原始数据后，在 Bridge 内部转换为对大模型高度友好的语义化结构：
- `user_id`: string (QQ 号)
- `display_name`: string (名片优先，无名片则使用昵称)
- `nickname`: string (QQ 个人昵称)
- `card`: string (群名片，未设置显示为 "未设置")
- `role`: string (语义化身份描述，如 `"群主 (owner)"`、`"管理员 (admin)"`、`"普通成员 (member)"`)
- `title`: string (专属头衔，无则显示为 "无")
- `join_time`: string (格式化加入时间与入群天数，如 `"2024-04-23 10:39:57 (已入群 186 天)"`)
- `last_sent_time`: string (格式化最后发言时间，如 `"2026-10-25 14:20:16"`)
- `level`: string (群活跃等级)
- `status`: string (`"正常"` 或 `"禁言中 (剩余 XX 秒)"`)
- `is_robot`: boolean (是否为官方机器人)

---

## 3. 架构设计与避坑准则

1. **规避单人接口超时**：
   实测证明 NapCat 的 `get_group_member_info` 接口在 NTQQ 下频繁挂起超时（8~10 秒并报错 1200）。底层统一采用全量群列表接口 `get_group_member_list`。
2. **TTL 内存缓存设计**：
   在 Bridge 内存中维护群成员列表缓存，默认 TTL 为 5 分钟（300,000 ms）。`no_cache: true` 时清除缓存并强制刷新。
3. **输出体积保护**：
   单次最多返回匹配的 Top 20 条记录，若匹配总数超过 20 条，附带 `total_matched` 与截断说明，防止 LLM 上下文爆炸。
