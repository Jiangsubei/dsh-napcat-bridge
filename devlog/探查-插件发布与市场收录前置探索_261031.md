### 2.2 2FA 与发布方式（关键约束）

npm 现行规则：发布需要「账号启用 2FA」或「启用 bypass-2FA 的 granular token」。

- 账号侧 2FA 状态无法通过当前 token 查询（403），**需实测 publish 时是否弹 OTP**
- npm 已公告：bypass-2FA token 的**直接发布能力将于 2027 年 1 月移除**；账号变更类操作（2026 年 8 月起）已要求交互式 2FA
- 若该 token 是 **stage-only**，`npm publish` 会报 `E_STAGE_REQUIRED`，需改用 `npm stage publish` + 维护者 2FA 审批

> 结论：**首次发布能否一条 `npm publish` 直接完成，必须实跑一次 dry-run 之外的定点验证**；存在被 2FA 或 stage-only 卡住的可能。

## 三、装配侧风险（最重要）

### 3.1 本项目 patch 比参考项目复杂

`cordis.patch.yml` 不只插入自身，还内嵌了一个完整的 `@deepseek-ai/dsh-agent-preset` 预设（`qq-session`），该预设再引用 12 个官方插件：

```
@deepseek-ai/dsh-agent-preset
@deepseek-ai/dsh-persona
@deepseek-ai/dsh-agent-instructions
@deepseek-ai/dsh-tool-fs
@deepseek-ai/dsh-tool-working-directory
@deepseek-ai/dsh-tool-workspace-dependencies
@deepseek-ai/dsh-tool-bash / dsh-tool-pwsh
@deepseek-ai/dsh-tool-web
@deepseek-ai/dsh-skill-filesystem / dsh-tool-skill
@deepseek-ai/dsh-tool-ask-user
```

对比 `dsh-qqbot-bridge` 的 patch —— 只 `insert` 自身一条，无任何外部包引用。

### 3.2 风险点

1. **12 个包全部未在 `peerDependencies` 声明**（现有 peerDeps 列的是 dsh-base/dsh-agent 等宿主服务包，不是这些工具包）。npm/pnpm 不会自动补装未声明的 peer。
2. **`@deepseek-ai/dsh-tool-working-directory` 版本线不一致**：npm 上最新为 `0.2.1-alpha.2`，而其余 11 个在 `@deepseek-ai/dsh@0.2.1-rc.5` 中均为 `0.2.1-rc.5`；且它**不是** `@deepseek-ai/dsh` 的直接依赖（由 `@deepseek-ai/dsh-base` 间接引入）。
3. 其余 11 个包经核对，**均为 `@deepseek-ai/dsh` 的直接 dependencies**，即标准安装的 DSH 环境天然具备。
4. 本地 `node_modules` 中 `@deepseek-ai/dsh-tool-working-directory` **不存在**（devDeps 未装该包），即当前无本地解析验证痕迹。

> 判定：**标准 DSH 环境下大概率可用，但 `dsh-tool-working-directory` 是单点脆弱环节**；一旦宿主移除或升版，`qq-session` 预设装配会整组失败。需在发布前决定是否补全 peer 声明或在 patch 中做可选化。

### 3.3 验证环境约束

- 本机 **无 `dsh` CLI**（PATH 中不存在；`npm root -g` 无 dsh）
- DSH 为 **Desktop 版**（`F:\Apps\DeepSeek Harness`），官方说明：`desktop` profile 由 Electron 独占，npm CLI **拒绝**对其执行插件管理
- 现存 profile：`desktop`（`@deepseek-ai/*` 目录为空壳，基线包在 Electron asar 内）、`napcat-test`（`node_modules` 中仅 `dsh-napcat-bridge` 一条，`cordis.yml` 为 `[]`）
- 当前 Web GUI：`http://127.0.0.1:56317`

> 含义：**「装完能不能跑」无法用 CLI 验证**，只能走 Desktop 的插件管理 UI（或其 Web GUI）做真机安装验证。这一步必须设计进发布流程。

## 四、DSH 插件市场侧

### 4.1 机制

DSH 自 2026-10-15 起支持插件市场，形态是**索引源（index.json）+ 各社区索引提供方**。用户侧在「插件 → 实验性插件 → 自定义插件市场」开启，再到「发现 → 添加索引源」粘贴索引地址。

DSH **没有统一的官方投稿入口**；能否被看到取决于被哪些索引收录。

### 4.2 主要投递通道

| 通道 | 规模 | 收录方式 | 门槛 |
| --- | --- | --- | --- |

### 8.2 关键修正：peer 声明必须 optional

原计划「直接补全 12 个 peer 声明」**经实测被证伪**：

- 在干净目录 `npm install` 该 tarball 直接 **ERESOLVE 失败**
- 根因：`@deepseek-ai/dsh-tool-working-directory` 从未发布稳定版，registry 的 `latest` 为 `0.2.1-alpha.2`；它 peer 要求 `@deepseek-ai/dsh-tools@0.2.1-alpha.2`，而宿主 `@deepseek-ai/dsh-base@0.2.0-rc.2` 要求 `dsh-tools@0.2.0-rc.2`，两套版本线直接冲突
- 另有 9 条间接 peer 冲突叠加

**采用的方案**：11 个工具/预设包保留 peer 声明（表达装配依赖），同时全部标记 `optional: true`。效果：

- 声明语义保留，宿主缺失时不再让 `npm install` 硬失败
- npm 不再自动安装这批包，避免版本线与宿主打架
- 实测 `npm install` 恢复正常（357 packages / 22s）
