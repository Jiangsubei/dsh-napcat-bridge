> **状态**: 需求讨论收敛，待用户审阅批注后定稿

## 0. 背景与目标

当前桥接已具备消息收发、Agent 工具、贴表情回应（`react_message`）、记忆回顾、设置卡等能力，但**没有表情包（图片表情）能力**：Agent 无法查看自己 QQ 号上的收藏表情，也无法在对话中"发个表情"。

本批新增：
- 本地表情库（唯一数据源）
- 表情包管理工具（`list_faces` / `send_face`）
- 设置卡新增「表情包管理」Tab（配额 / 列表 / 启停 / 删除）
- 后台定期整理：从已落盘图片中识别表情包、移入表情库、打语义标签

**核心设计决策（本批总纲）**：
> **1. 本地表情库是唯一数据源，不操作、不镜像 QQ 收藏表情。**
> 理由：维护两套（本地库 + QQ 收藏）会产生持续漂移与对账成本；配额、启停、标签、删除这些管理能力 NapCat 收藏体系无处承载，管理面只能落在本地。
>
> **2. 能力判断交给用户与模型，应用层不做兜底。**
> 理由：与既有「赋能但不替 Agent 做决定」哲学一致。模型不能读图就自己输出 `nothing to save`，应用层不探测、不降级、不拦截。
>
> **3. 整套功能由一个 Tab 总开关门控，默认关。**
> 理由：避免无人开启时产生后台活动；由用户按需启用。

## 1. 术语与边界

| 术语 | 含义 | 本批处理 |
|---|---|---|
| 本地表情库 | 桥接侧落盘的图片文件 + 索引（含语义标签、启停状态） | ✅ 本批核心 |
| QQ 收藏表情（fav emoji） | QQ 客户端"表情收藏"里的表情，`fetch_custom_face` 可列 | ❌ 不读取、不写入、不镜像 |
| 商城表情（mface） | QQ 表情商城的表情，有 `emoji_id`/`emoji_package_id`/`key` 身份 | ❌ 不涉及 |
| QQ 内置表情（face） | 小黄脸那套，走 `face` 消息段 | ❌ 已由 `react_message` 覆盖，本批不动 |

## 2. 关键结论（调研所得，实现依据）

### 2.1 发送形态：走 image 消息段
- 本地图片只能通过 `image` 消息段发出，其发送字段为：`file`（路径/URL/base64，必填）、`name`、`summary`、`sub_type`（均为可选）。
- **不能走 `mface`**：`mface` 消息段必填 `emoji_package_id`、`emoji_id`、`key`、`summary` 四个身份字段，而本地自建表情没有这套身份（QQ 收藏表情同样取不到，这正是 `fetch_custom_face` 只返回 URL 的原因）。
- `sub_type` 是唯一可能让图片以"表情"形态渲染的入口，但官方文档只列字段名、**未给取值表**，必须实测确定（见第 3 节）。

### 2.2 可用的 NapCat 接口（备查）
| 用途 | 接口 | 关键参数 |
|---|---|---|
| 列出收藏表情（仅 URL） | `fetch_custom_face` | `count`（默认 48） |
| 收藏表情详情 | `fetch_custom_face_detail` | `count`（默认 48） |
| 添加收藏表情 | `add_custom_face` | `file`（本地路径，必填）、`emoji_id`（空串）、`package_id`（0）、`file_name`、`file_size`、`md5`、`is_mark_face`、`is_origin` |
| 删除收藏表情 | `delete_custom_face` | `res_id`/`id`/`ids`/`md5`（md5 不能直删，需先取 `resId`） |
| 修改描述 | `set_custom_face_desc` | `emoji_id`、`res_id`、`md5`、`desc` |

> ⚠️ 上述表情增删改接口为 NapCat 较新版本新增（2026-06/07 进入文档，最新文档版 v4.18.19）；旧版本调用会返回未知 action。**本批不使用这些接口**，仅作背景记录。

## 3. 开工前实测（必做，阻塞实现）

> 三项验证全部有结论后，方可进入实现。实测结果回填本节。

- [ ] **M1 · `image` 段 `sub_type` 渲染形态**
  - 构造同一张本地图片，分别以 `sub_type` 缺省 / 各候选值发送到测试群与私聊，逐张截图记录 QQ 侧渲染结果（是否呈表情形态、是否被压、是否显示为文件卡片、是否变形）。
  - 产出：`sub_type` → 渲染形态对照表；确定表情发送应采用的值（或确认无解）。
- [ ] **M2 · 尺寸与压缩边界**
  - 同一张图以不同分辨率/格式（含透明 PNG、GIF、WebP）发送，记录是否被压缩、动图是否保活。
  - 产出：表情库的推荐存储格式与尺寸上限。
- [ ] **M3 · 发送复用性**
  - 确认发送本地图片时能否复用已上传资源（避免每次重传）。`image` 段的 `file_id` 在文档中标注为 **[收]**，需实测确认发送侧是否接受。
  - 产出：发送路径结论（每次重传 / 可复用）。

**M1 结论决定第 5.3 节 `send_face` 的最终形态。**

## 4. 需求 A：本地表情库

### 4.1 存储结构
- 表情文件落盘目录（默认 `napcat_download/face/<peer 无关，全局共享>/`），仅存**原图**（不存压缩版）。
- 索引文件（JSON 或 SQLite，实现期定）每条记录：
  ```
  { id, file, md5, added_at, source, tags[], mood, enabled, size, format, last_used_at, use_count }
  ```
  - `source`：来源（后台整理 / 手动导入 / 消息收藏）
  - `tags[]`：内容标签（如 猫 / 熊猫头 / 文字表情）
  - `mood`：情绪语义（如 嘲讽 / 赞同 / 无语 / 卖萌）
  - `enabled`：是否允许发送

### 4.2 语义标签是核心价值
- 无标签的表情库对模型等价于"一堆路径"——和直接调 NapCat 拿 URL 列表没有区别。
- 有标签才能让 Agent 按语境选表情，这是本地库相对直连 NapCat 的**唯一实质增益**。
- 标签来源优先级：
  1. 后台整理时由模型看图生成（主路径）
  2. 必要时人工在设置卡修正/补充（见 5.1）

### 4.3 配额与淘汰
- 配置项「最多存多少张」；达到上限时行为：
  - 默认：**拒绝新增**（后台整理跳过、手动导入报错），不自动删除。
  - 可选：按 `last_used_at` 淘汰最久未用的（需显式开启）。
- 不自动删用户手动导入的表情。

### 4.4 去重
- 以 `md5` 为唯一键；同图重复出现（不同来源）不重复入库，只更新 `last_used_at` / 补充标签。

## 5. 需求 B：功能模块

### 5.1 表情包管理 Tab（Web UI 设置卡）
- 设置卡新增 Tab：**表情包管理**（与既有 Tab 体系一致，沿用现有分区/分组样式）。
- **Tab 内置总开关（`face_enabled`）**：默认关，用户按需开启。
  - 关 = 表情库不启用、工具不注册、后台整理任务不运行（不产生任何后台活动）。
  - 开 = Tab 内各项设置生效，工具注册，后台整理按配置周期运行。
- 内容（仅总开关开启后可见/可操作）：
  1. **配额设置**：最多存多少张（数字输入）
  2. **表情列表**：缩略图 + 标签 + 启用开关 + 删除按钮
  3. **批量操作**：启用/禁用、删除
  4. **手动导入**：选择本地文件入库
  5. **标签编辑**：可手工修正 `tags` / `mood`
- 交互粒度与既有设置卡保持一致（不做运行时审批）。

### 5.2 后台定期整理
- 形式：类现有 background review 的定期任务，**受 Tab 总开关门控**（开关关闭时不注册、不运行）。
- 输入：**已落盘的图片库**（入站图片目录，即 `napcat_download/image/<peer>/`）。
- 动作：
  1. 扫描图片，判定是否为表情包（判定标准见 §7 待确认 Q1）
  2. 判定为表情包的 → 移入表情库目录
  3. 生成 `tags[]` / `mood`
  4. 按 md5 去重、按配额门控
- **注意**：本任务只做"看图 + 打标签 + 移动文件"，**不生成 skill、不写记忆**（与既有约定一致）。
- **模型能力不做兜底**：不检测、不假设运行模型是否具备读图能力。
  - 有读图能力 → 正常识别与打标签。
  - 无读图能力（纯文本模型）→ 模型自行判断为无可保存内容，输出 `nothing to save`，本轮整理不产出任何条目。
  - 应用层不做能力探测、不做降级分支、不做报错拦截；判断权完全交给模型。
  - 用户按需自行决定用哪个模型跑该任务。

### 5.3 Agent 工具：`list_faces` / `send_face`
| 工具 | 签名（初稿） | 说明 |
|---|---|---|
| `list_faces` | `{ mood?, tag?, limit?, cursor? }` | 返回**分页**的简要列表（id + 标签 + 情绪），**绝不返回全量** |
| `send_face` | `{ face_id }` | 按 id 发送表情到当前会话 |

- **分页是硬要求**：本地库可能有几十上百张，全量列表灌进上下文会挤爆 token（NapCat 的 `fetch_custom_face` 一次 48 条长 URL 就是反面教材）。
- `list_faces` 只返回 id 与语义标签，不返回文件路径与 URL。
- `send_face` 内部把 id 解析为文件路径，按 M1 实测结论构造 `image` 段发送。
- 会话范围：群聊 + 私聊均可（表情非群专属能力）。
- 是否注册由开关前置门控（见 5.5）。

### 5.4 行为准则（引导，非门控）
- 提示词中说明：可以在合适语境下用 `send_face`，但不要滥用、不要连续发。
- 与既有"能力门控 vs 使用引导"哲学一致：低风险能力常驻、由 Agent 自决。

### 5.5 配置项
| 配置 | 默认 | 说明 |
|---|---|---|
| `face_enabled` | 关 | **表情包 Tab 总开关（设置在 Tab 内）**；关 = 表情库不启用、工具不注册、后台整理不运行 |
| `face_store_max` | 待定 | 表情库容量上限 |
| `face_store_dir` | `napcat_download/face/` | 表情库目录 |
| `face_auto_curate` | 关 | 后台定期整理开关（仅在总开关开启时有效） |
| `face_curate_cron` | 待定 | 整理周期 |
| `face_sub_type` | 待 M1 结论 | 发送时使用的 `sub_type` 值 |
| `face_evict_policy` | `reject` | 满额行为：`reject` / `evict_lru` |

## 6. 不做的事（明确排除）
- ❌ 不读取 / 写入 / 镜像 QQ 收藏表情（不调 `fetch_custom_face` 系列）
- ❌ 不做 mface 商城表情
- ❌ 不改动既有 `react_message`（QQ 内置表情回应）
- ❌ 不在后台整理流程里建 skill / 写记忆
- ❌ 不做运行时审批（沿用开关前置门控）
- ❌ 不做模型能力探测与兜底（是否具备读图能力由模型自判，读不了就 `nothing to save`）
- ❌ 不假设用户的模型部署方式（本地 / 远程 / 哪套工具，均不预设）

## 7. 待确认（需用户批注）

- **Q1**：后台整理"判定为表情包"的标准，是**完全交给模型自由判断**（不加尺寸/格式等硬条件），还是由应用层先做粗筛（如尺寸 ≤ 500×500 + 常见表情格式）再交模型？请批注取向。
- **Q2**：表情库配额默认值定多少？
- **Q3**：满额时默认拒绝还是淘汰最久未用？
- **Q4**：`use_count` / `last_used_at` 是否需要（用于后续做"常用表情优先"）？
- **Q5**：表情是否分群隔离（同一表情库全局共享，还是按群独立）？建议全局共享。
- **Q6**：是否需要"表情只发不收"——即别人发的表情要不要自动进候选池？建议只走后台整理，不实时收录。

## 8. 风险
| 风险 | 说明 | 缓解 |
|---|---|---|
| 渲染形态不确定 | `sub_type` 无文档，可能根本无法渲染成表情形态 | M1 实测；若不可行，退化为普通图片发送并如实告知用户 |
| 上下文成本 | 表情数量增长导致 `list_faces` 输出膨胀 | 强制分页 + 只回标签不回路径 |
| 存储膨胀 | 长期整理积累大量图片 | 配额硬上限（4.3） |
| 与 QQ 收藏的功能差异 | 本地表情不会出现在用户手机 QQ 的表情面板里 | 本批明确接受此限制（不维护两套的代价） |
