## 1. 背景与 15 张图片实测定位

### 1.1 现状与问题表现
在引入四段式取图落盘机制（`get_image` → `get_file` → `url` → `get_msg`）后，外来图片与表情包的有效落盘率得到保障。然而在实际使用中偶发以下瓶颈：
1. **表情包卡顿 10~20 秒**：部分入站表情包在收到后，Bridge 侧卡顿 10~20 秒才落盘完成；
2. **多图串行阻塞**：入站消息若包含多张图片，逐张串行拉取导致延迟线性累加；
3. **设置面板冗余顾虑**：若通过新增配置项（如用户手动填写数据目录）来解决同机直读，会给使用者增加配置心智负担。

### 1.2 15 张图片实测对比数据
通过反向 WebSocket（端口 3001）连入真实 NapCat 实例，收集 15 张真实样本并进行 5 链路实时对比测速：

| 样本类型 | 样本数量 | 本地直读 (`nt_cache`) | NapCat `get_file` | NapCat `get_image` | HTTP 直链 (`url`) |
| :--- | :---: | :---: | :---: | :---: | :---: |
| **普通图片** (`sub_type: 0`) | 9 张 | **0.73ms ~ 7.0ms (100% 命中)** | 10ms ~ 47ms | 29ms ~ 819ms | 146ms ~ 545ms |
| **自定义动画表情** (`sub_type: 1`) | 2 张 | **0.74ms ~ 7.3ms (100% 命中)** | 7ms ~ 38ms | 27ms ~ 311ms | 193ms ~ 378ms |
| **QQ 商城/官方大表情** (`[摆烂]`, `[思考]` 等) | 4 张 | 磁盘位于 `marketface` 目录 | **❌ 10004ms 必超时** | **❌ 10006ms 必超时** | **✅ 117ms ~ 255ms (100% 成功)** |

### 1.3 核心瓶颈根因确证
1. **商城表情超时元凶**：
   - QQ 商城官方大表情（带有 `emoji_package_id` 或 host 为 `gxh.vip.qq.com`）在 NTQQ 底层属于 `marketFaceElement`，并不走常规富媒体消息监听；
   - NapCat 的 `get_image` 与 `get_file` 调用 `FileApi.downloadMedia` 监听事件时，NTQQ 绝不触发回调，导致 NapCat 处于挂起等待状态直至超时（10秒 + 10秒 = 20秒）；
   - 但其 `url`（`https://gxh.vip.qq.com/.../raw300.gif`）属于永久有效的静态公开 CDN，直接 HTTP 下载仅需 100~200ms。
2. **零配置自动发现确证**：
   - Windows 平台通过读取公共配置 `C:\Users\Public\Documents\Tencent\QQ\UserDataInfo.ini` 中的 `UserDataSavePath`，可 100% 全自动识别出用户数据根目录（实测全自动穿透识别，无需用户手动配置）；
   - 动态学习机制（`learnNtqqDirFromPath`）会在任何一次成功返回物理路径时自动记忆根路径。

## 2. 方案架构与实现设计

### 2.1 整体架构：智能自适应选路流水线 (Smart Adaptive Routing)

```text
[入站图片 / 表情消息段]
       │
       ▼
【第 0 段：一级内存/DB去重】 ────────── 命中 ──> [直接复用 downloads/ (via: cache)]
       │ 未命中
       ▼
【第 0.2 段：同机 NTQQ 缓存零配置直读】 ─ 命中 ──> [复制至 downloads/ (via: nt_cache，耗时 ~1ms)]
       │ 包含: Pic/YYYY-MM/Ori, Emoji/emoji-recv, Emoji/marketface
       │ 未命中
       ▼
【第 0.5 段：段内 local_path 归一】 ─── 命中 ──> [复制至 downloads/ (via: segment_local_path)]
       │ 未命中
       ▼
【特征分支判断：是否为商城官方表情 / 静态公开 CDN？】
       ├─ 是 (带 emoji_package_id 或 host 为 gxh.vip.qq.com)
       │       │
       │       └─> 【直接走 HTTP 直链】 ── 成功 ──> [落盘 (耗时 ~100ms，坚决跳过 get_image/get_file)]
       │
       └─ 否 (常规图片 / 普通表情)
               │
               ▼
       【第 1 段：NapCat get_image】 ── 成功 ──> [复制至 downloads/ (via: get_image，5s 超时收敛)]
               │ 失败 / 超时
               ▼
       【第 2 段：NapCat get_file】 ─── 成功 ──> [复制至 downloads/ (via: get_file，5s 超时收敛)]
               │ 失败 / 超时
               ▼
       【第 3 段：HTTP 直链兜底】 ───── 成功 ──> [下载至 downloads/ (via: url)]
               │ 失败
               ▼
       【第 4 段：get_msg 刷新直链】 ── 成功 ──> [下载至 downloads/ (via: get_msg_url)]
```

### 2.2 零配置与设置面板设计
1. **彻底不加新配置项**：
   - Schema 维持原有的 38 项核心配置，移除 `napcat_data_dir`；
   - 避免向用户暴露技术性内部路径，实现零配置开箱即用。
2. **Tab 1 命名优化**：
   - Web UI Tab 1 保留重命名为「连接设置」（`{ id: 'connection', label: '连接设置' }`），更加通用明确。

### 2.3 多图异步并发解析流水线
在 `src/index.ts` 收到入站 `message` 事件时：
- 提取消息内所有的 `image` 段；
- 使用 `Promise.all` 并发调用 `resolveInboundImage`；
- 所有图片异步并发拉取/直读，彻底消除多图串行累加延迟；
- 依次写回各消息段的 `data.local_path`，并以首张成功图确立 `primaryLocalPath`。

## 3. 验收标准与契约验证

1. **Tab 1 重构验证**：
   - `SETTINGS_TABS` 首项 label 为「连接设置」；
   - Tab 1 包含 6 项核心配置；
   - Schema / Server / Client 三方有效键保持 38 项严格一致。
2. **直读缓存契约**：
   - 同机缓存存在时（含普通图、动图与 `marketface`），`resolveInboundImage` 返回 `via: 'nt_cache'`，且不调用 `gateway.getImage`。
3. **商城表情直通契约**：
   - 当收到商城表情且本地未命中时，直接走 HTTP 直链（`via: 'url'`），绝不调用 `getImage`/`getFile`，消除 10 秒超时挂起。
