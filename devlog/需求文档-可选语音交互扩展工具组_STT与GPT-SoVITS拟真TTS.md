## 0. 背景与设计动机

目前 `dsh-napcat-bridge` 已支持完善的文本交互、表情包检索与动态情绪锚点、图片识别与文件收发，但在**声音维度（语音输入与语音输出）**尚处于空白阶段。

在 QQ 社交场景中，语音具有极高的拟人化价值与沉浸感。然而，现有的语音 Bot 往往面临以下痛点：
1. **无差别转写打爆算力**：群聊中所有闲聊语音全部自动跑 STT，导致并发极高、GPU 显存暴涨、大量算力浪费在与 Bot 无关的消息上；
2. **死板的被动应答机制**：要么每条消息都强行转成语音，要么死板设定“收到语音才回语音”，丧失了大模型根据语境自主决策的灵活性；
3. **“无菌室感”与恐怖谷效应**：传统 TTS 生成的人声背景是绝对的数字纯静音（Digital Silence），缺乏真实物理环境的空气感（Room Tone）与底噪，听感冰冷机械，一耳朵即可识别为 AI；
4. **环境依赖沉重，污染主程序**：深度学习推理框架（PyTorch/CUDA/模型权重）体积庞大，若直接揉入轻量级的 Node.js 插件中，会导致部署灾难。

针对上述问题，本项目设计了一套**高内聚、弱耦合的可选语音交互扩展工具组（Audio Toolset）**。

## 1. 架构总纲：独立伴生服务（Sidecar）与标准适配层

│             │                                │              │
│   ┌─────────┴──────────┐         ┌───────────┴──────────┐   │
│   │ silk-wasm 转码管线 │         │ 轻量环境音混音管线   │   │
│   └─────────┬──────────┘         └───────────┬──────────┘   │
└─────────────┼────────────────────────────────┼──────────────┘
              │ (HTTP / REST API)              │
              ▼                                ▼
┌─────────────────────────────────────────────────────────────┐
│          独立伴生仓库 (Python / C++ 推理服务 Sidecar)       │
│                                                             │
│  - 本地 STT 推理: SenseVoice-Small (ONNX / sherpa-onnx)      │
│  - 本地 TTS 推理: GPT-SoVITS 深度优化推理引擎                │

│  - 一键启动包 / 国内源模型权重加速下载                      │

              ▲

└─────────────────────────────────────────────────────────────┘

### 1.1 核心原则
1. **主项目保持极致轻量**：主工程只保留协议封装、Silk/WAV 互转（纯 WebAssembly 实现）、音频混音和工具注册逻辑，不引入任何重型深度学习依赖；
2. **标准接口同构（API-First）**：主插件通过标准 REST API 与伴生服务通信；无独显或低配机器可零代码修改无缝切换至火山引擎等云端 API；
3. **独立仓库分发**：伴生服务独立开设 GitHub 与 Gitee 仓库，负责 Python 环境、整合包打包、模型分发与本地推理延迟优化。

## 2. STT（语音转写）需求规格：双轨触发与算力保护

为了彻底避免群聊中闲聊语音挤爆显存和浪费算力，STT 采取**“直接唤醒自动转写 + 滑动窗口按需工具化”**的双轨策略。

### 2.1 轨迹 A：明确找 Bot 消息（自动转写）
- **触发条件**：私聊消息、群聊中 @Bot 或命中唤醒前缀的消息；
- **处理链路**：
  1. NapCat 收到语音消息段（Silk 格式）；
  2. 桥接层自动调用 `silk-wasm` 解码为 WAV 音频；
  3. 调用 STT 服务转写为文字；
  4. 拼接入站上下文，显式打标：
     ```text
     [用户发来语音（语音转文字）]: "你好呀，今天有空聊聊吗？"
     ```
- **设计价值**：大模型无需额外产生一次 Tool Call 轮次，响应迅速；同时标明“语音转文字”可让大模型自然容忍口语化错别字和语气词。

### 2.2 轨迹 B：群聊滑动窗口历史（惰性保存 + 工具化按需回溯）
- **触发条件**：群聊中未 @Bot、群友之间互发的闲聊语音；
- **处理链路**：
  1. **严禁自动转写**，阻断并发算力消耗；
  2. 桥接层仅将语音下载并保存至本地附件目录（如 `attachments/voice/voice_1730000000.wav`）；
  3. 在呈现给大模型的滑动窗口历史中占位呈现：
     ```text
     [群友张三 发送了一条语音消息，本地音频路径: attachments/voice/voice_1730000000.wav]
     ```
  4. **注册 `transcribe_voice` 按需工具**：
     - 若大模型认为上下文无关，则直接忽略（省下 100% 转写算力）；
     - 若大模型需要深入理解群友讨论内容或被追问“刚才那条语音说了什么”，大模型可**主动调用工具**进行转写。

### 2.3 STT 工具定义 (`transcribe_voice`)
```ts
interface TranscribeVoiceParams {
  /** 待转写的本地音频文件路径（从历史上下文占位符中获取） */
  file_path: string;
}

interface TranscribeVoiceResult {
  /** 转写出的文本内容 */
  text: string;
  /** 可选：情感或声音事件标签 (如 SenseVoice 识别出的 [开心]、[笑声]) */
  emotion?: string;
}
```

### 2.4 模型选型
- **本地默认**：阿里开源 `SenseVoice-Small`（通过 ONNX / sherpa-onnx 驱动）；
  - 体积约 200MB ~ 300MB，完全符合 1GB 内存内要求；
  - 极速非自回归架构（推理延迟数十毫秒，远超 Whisper）；
  - 支持中英文、粤语及富文本声音事件（笑声、掌声等）；
- **云端备选**：火山引擎语音大模型 STT（提供 API Key 即用）。

## 3. TTS（语音合成）需求规格：GPT-SoVITS 与拟真环境混音

### 3.1 核心机制：大模型自主决定发语音
- **行为准则**：发语音不是机械规则，而是作为**主动工具 `send_qq_voice`** 暴露给大模型；
- 大模型根据语境自主决定：日常交流输出普通文字；当需要撒娇、讲述故事、情绪表达或用户要求听声音时，大模型自主调用 `send_qq_voice`；
- **出站纯粹性**：调用工具后直接通过 NapCat 发送 QQ 原生语音条（Silk 格式），**桥接层不追加任何额外的文字解释**，保持交互真实纯粹。

### 3.2 恐怖谷破解：纯代码模拟环境底噪（Ambient Noise Mixing）
- **痛点根因**：传统 TTS 输出绝对静音（Digital Silence），人耳在字句停顿处会产生强烈的虚假感与“无菌室假人”恐怖谷效应；
- **混音方案**：
  1. 预置极轻量的微小环境音频片段库（微风、室内空气底噪、机械键盘敲击、咖啡厅背景声、下雨声等）；
  2. TTS 生成干净人声 WAV 后，代码层通过毫秒级混音算法（Audio Mixing）将指定环境音以较低电平（-18dB ~ -24dB）叠加至底层；
  3. 首尾施加毫秒级淡入淡出（Fade-in / Fade-out）；
  4. 既打破了恐怖谷效应，又赋予 Agent 真实的“物理场景具身感”。

### 3.3 语音发送工具定义 (`send_qq_voice`)
```ts
interface SendQQVoiceParams {
  /** 语音需要朗读的文本内容（建议为适合口语表达的台词，不含 Markdown、链接等） */
  text: string;

  /** 
   * 可选：模拟真实环境声（消除纯净 TTS 的 AI 假人感，增强具身感与真实感）
   * - "none": 不叠加任何环境音
   * - "room": 轻微室内空气底噪（推荐日常使用，打破数字纯静音）
   * - "keyboard": 机械键盘敲击声（适合“正在玩电脑/码字”的情境）
   * - "wind": 户外微风声（适合“在外面/在路上”的情境）
   * - "cafe": 咖啡馆低语环境声
   * - "rain": 窗外雨声
   */
  ambient?: "none" | "room" | "keyboard" | "wind" | "cafe" | "rain";

  /** 
   * 可选：GPT-SoVITS 情绪音色倾向（匹配对应的参考音频底模）
   * - "neutral": 默认自然语气
   * - "happy": 开心、活泼
   * - "tsundere": 傲娇、轻微嗔怪
   * - "sad": 低落、委屈
   */
  emotion?: "neutral" | "happy" | "tsundere" | "sad";
}
```

### 3.4 硬件门槛与选型
- **模型选型**：GPT-SoVITS（兼顾极致音色克隆与高度情感表现力）；
- **硬件标称**：作为可选功能，明确在功能说明中告知用户：
  > “开启本地高质量拟真语音（GPT-SoVITS）建议配置：NVIDIA 显卡 6GB+ 独立显存（RTX 2060 级别及以上），方可获得低延迟交互体验。”
- **云端替代**：火山引擎语音合成 TTS，供无独立显卡或低配设备选用。

## 5. 协议与工程链路细节

1. **Silk 编解码纯轻量化**：
   - 依赖 `silk-wasm` 进行双向转码（Silk ⇄ PCM/WAV），不强依赖用户操作系统安装重型 `ffmpeg` 命令行程序；
2. **DSH Lossless JSON 输出红线**：
   - 工具执行返回结果必须经过 `toLosslessJson()` 递归清洗，严禁含有 `undefined` 字段，严格对齐项目规范；
3. **文本口语化清洗（Text Sanitizer）**：
   - 在工具描述或参数描述中说明送给 TTS 模型的文本规范。
